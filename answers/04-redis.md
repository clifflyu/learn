# 04 · Redis 与缓存（Q25–Q31）

> 配套 `../php-senior-interview-top50.md`。数字均来自容器实测（Redis 7.4.11 / MySQL 8.4.11 / PHP 8.4.25），脚本在 `../bench/redis/`。

## Q25. Redis 为什么快？「单线程」的边界在哪？

### 结论

快来自三条：**纯内存 + 命令执行单线程免锁 + IO 多路复用**。「单线程」只描述**命令执行**那一段——Redis 7 的 `io-threads` 已经把 socket 读写和协议解析分出去了。这条边界的实际含义是：**一条 O(N) 命令会让所有客户端一起等，加 io-thread 一点用都没有**。实测用 Lua 忙等 3 秒，一条 `PING` 等了 **4,707 ms**；把 `io-threads` 从 1 调到 4，还是等 **4,721 ms**。

而真实吞吐瓶颈通常不在 Redis 的处理速度，在**每个命令一个网络往返**：单连接 `-P 1` 只有 **8,573 rps**，把 pipeline 开到 64 深到 **416,667 rps**（同一轮内 48.6 倍）。拿不到理论上的 64 倍，差额就是主线程这时候已经跑满了。

### 一、边界在哪

```
   客户端 A ─┐
   客户端 B ─┤   ┌───────────────────────────────────────┐
   客户端 C ─┼──►│  io-threads（默认关闭，=1 就是没有）    │
     ...     │   │  只做：read() / 协议解析 / write()      │
   客户端 N ─┘   └──────────────────┬────────────────────┘
                                    │ 解析好的命令，排队
                                    ▼
                  ┌──────────────────────────────────────┐
                  │  主线程：事件循环 + 命令执行            │  ◄── 永远只有一个
                  │  一条 O(N) 命令在这里跑 4.7 秒，        │
                  │  后面排队的全部客户端一起等              │
                  └──────────────────┬───────────────────┘
                                     ▼
                             内存里的数据结构
```

三个「快」的来源，分别对应三个可证伪的边界：

| 说法 | 边界在哪 |
| --- | --- |
| 纯内存 | 只省掉磁盘 IO，不省 CPU。单条 `SET` 服务端仍要烧掉约 1.6 µs |
| 单线程免锁 | 免的是**同一份数据**上的锁；代价是 O(N) 命令会阻塞所有人（实测 4.7 s） |
| 多路复用 | 解决的是「同时等很多连接」，不解决「一个连接等一个往返」 |

**一次 `SET` 的耗时构成**（`-c 1 -P 1`，实测 8,573 rps）：

```
  客户端             网络              Redis 主线程
    │                 │                    │
    ├── SET k v ─────►│──── 0.058 ms ─────►│  执行 SET：约 1.6 µs
    │                 │                    │
    │◄──── +OK ───────│◄─── 0.058 ms ──────┤
    │
    一次往返 ≈ 0.117 ms，Redis 自己只干了 1.6 µs  → 1.3%
    → 单连接 rps ≈ 1 / 0.000117 ≈ 8,570   （实测 8,573）
```

所以「Redis 快」对单连接的日常用法是**帮不上忙的**——**98.7%** 的时间花在等网络上，Redis 在闲着。

> **源码对照**：`io-threads` 的实现在 `networking.c` 的 `handleClientsWithPendingReadsUsingThreads()` / `handleClientsWithPendingWritesUsingThreads()`，线程池只调 `readQueryFromClient()` 和 `writeToClient()`。命令执行入口 `processCommand()` 只在主线程的 `beforeSleep()` → `processInputBuffer()` 链路上被调用，从未进过线程池。

### 三、四个反直觉的点

**1. 「先跑完 A 的 5 次、再跑 B 的 5 次」这种顺序扫描，在这台机器上会给出完全错误的方向。** 实测第 2 节的表看着像 `io-threads=4` 比 `=1` 快 1.24 倍；同一份代码换成交错配对（一轮里交替跑两个配置），中位差是 **−2,268 rps**，符号反了。**这不是 io-threads 的问题，是测量方法的问题**——机器上还跑着别的容器，一段时间忙一段时间闲，顺序扫描会把「机器闲下来」记成「配置 B 更好」。

**2. `usec_per_call` 不是「命令的 CPU 成本」。** 同一个 `SET`，`-c 1` 下 1.57 µs，pipeline 下 0.21 µs——命令本身没变（差 7.5 倍）。差别在于 `usec` 是从「开始处理这条命令」到「回复写完」的墙上时间，**包含了这条命令引发的 socket 读写系统调用**。`-c 1` 时每条命令都要各自绕一圈 epoll，pipeline 时一次系统调用摊给几十条命令。拿这个数去算「单线程能跑多少 QPS」会严重低估。

**3. pipeline 64 深只拿到 43.6 倍，不是 64 倍——说明主线程这一刻成了瓶颈。** 如果 Redis 处理快到可以忽略，pipeline 应该线性摊薄 RTT，实测应该接近 64 倍。实测 6 轮中位 43.6 倍，缺口就是此时单条命令的服务端成本——再去加深 pipeline 收益会迅速变平。

**4. `io-threads` 要的是「Redis 自己的线程在 socket 读写上先饱和」，本环境远没到。** 这台机器上 `-c 50` 的吞吐（4~6 万 rps）离主线程上限还很远，而且压测客户端（`redis-benchmark` 和 Redis 进程在同一台机器上）会和 Redis 抢同一批 CPU——**加线程反而多一层竞争**。**生产上要判断该不该开，唯一可靠的办法是同步压测下看 Redis 进程的 CPU 是否已经打满单核。**

**5. 单连接的 RTT 就是天花板，而且这个天花板比想象的低。** 实测 `-c1 -P1` 只有 8,573 rps，而握手级 RTT 只有 0.117 ms（容器网络，本机）。**换成跨机房的 0.5 ms RTT，单连接立刻掉到 2,000 rps。** 这是「Redis 快不代表你的链路快」的量化版本。

### 四、实战结论

| 场景 | 结论 |
| --- | --- |
| 单连接做大量小命令 | 无论怎么优化 Redis 都没用，98.7% 时间在等网络。改 pipeline 或换 `MGET`/`MSET` 批量接口 |
| 生产要不要开 `io-threads` | 本环境测不出收益，**不能作为推荐依据**。按官方口径是「同步压测下 QPS 上不去且 Redis 进程 CPU 已满」才开，通常 `io-threads=4` 起步、不超过核数 |
| 慢命令排查 | `SLOWLOG`（默认 >10 ms 记录）+ `LATENCY DOCTOR`。重点盯 O(N) 命令：`KEYS`、`HGETALL`、`SMEMBERS`、`LRANGE k 0 -1`、`SORT`、`DEL` 大 Key |
| 禁止的线上命令 | `KEYS` 一定要换成 `SCAN`（`KEYS` 是 O(N) 且必阻塞）；`DEL` 大 Key 换 `UNLINK`（见 Q31） |
| 吞吐上不去 | 先看是不是 RTT 受限（单连接 rps × 0.117 ms ≈ 1），再看 pipeline 深度，最后才看 `io-threads` |
| 压测方法 | **必须交错配对多轮取中位**。实测顺序扫描给出的方向是错的（见反直觉点 1） |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| 为什么用单线程而不是多线程？ | 免锁带来的是「可预测的延迟」和「简单的实现」。多线程版（如 Memcached）要处理数据竞争，热点 key 上的锁开销会抵消并行收益。Redis 选择把并行放到「不碰数据」的地方：io-threads 做 IO、bio 线程做 `UNLINK` 释放和 fsync |
| 单线程是不是意味着只能用 1 个 CPU？ | 不是。实测容器可见 8 核：主线程 1 个核，bio 线程、`io-threads` 各自占核。但**命令执行**确实只用 1 个核，所以单实例的上限由单核决定 |
| 那怎么用满多核？ | 起多个实例（每核一个），前面用 Cluster 或客户端分片。代价是跨实例操作（`MGET` 多 key、事务、Lua）不再可用 |
| `io-threads` 和 `io-threads-do-reads` 什么关系？ | `io-threads` 只并行化**写回复**；读请求的解析要额外打开 `io-threads-do-reads yes`。实测表里两列都给了，同样测不出差异 |
| Redis 6 的多线程和 7 有区别吗？ | 机制一致。7 的主要变化是 AOF 改多 part、`FUNCTION`、以及 `io-threads` 的一些调度细节。本环境只在 7.4.11 上实测 |
| `LATENCY` 怎么看？ | `redis-cli --latency` 看本机往返分布，`--latency-history` 看随时间的变化，`LATENCY RESET` + `LATENCY LATEST` 看服务端记录的事件（`command`、`fork`、`expire-cycle` 等）。本文的「旁人最坏 PING」就是手工版 `--latency` |
| 6.0 之前为什么没有 io-threads？ | 不是不能做，是没必要——瓶颈在内存和网络，不在 CPU 的 read/write 上。真正的驱动力是 40 Gbps 网卡和 TLS 握手开销 |

## Q26. 常用数据结构与业务场景

### 结论

五种基础结构在同一批数据上的边际内存差 **5 倍以上**：list **18.1 B/元素**、set **55.7**、hash **71.7**、string **80.0**、zset **96.2**。

但真正决定开销的不是「选了哪个结构」，而是**编码**。所有小对象都以 listpack 连续存放，一旦越过阈值就转成 hashtable / skiplist，内存**跳一个台阶**：

```
  同样是「10 万条数据，用 hash 存」，只改每片放多少字段

   B/条
    88 ┤ ●  每片 1 个字段（等于 10 万个独立 hash key）
       │
    72 ┤                                    ●  每片 513 个字段
       │                                    │      ↑ 转 hashtable
    64 ┤                              ●     │  每片 1000 个
       │                              │     │
    20 ┤        ●───────●───────●─────┘     │
       │      每片128  每片400  每片512      │
     0 ┼───────┴───────┴───────┴────────────┴──────►
        listpack（连续内存，无字典）      hashtable（每字段一个 dictEntry）
                                         悬崖就在 512 → 513
```

所以「用 hash 省内存」只在小 hash 时成立：每片 512 字段时 **20.1 B/条**，改成 513 就变 **71.9 B/条**（3.6 倍）。而 10 万个独立 string key 是 **72.0 B/条**，和「一个大 hash」的 71.7 几乎一样——**「key 太多浪费内存」这个说法被高估了**。

### 一、数据结构和它们的场景

| 结构 | 底层（小 / 大） | 典型场景 | 别拿它做 |
| --- | --- | --- | --- |
| string | int / embstr / raw | 计数器（`INCR`）、缓存 JSON、分布式锁、位图（`SETBIT`） | 存大 JSON 再整取整存（改一个字段也要全量搬） |
| hash | listpack / hashtable | 对象字段（用户资料）、购物车、**小规模分片** | 无脑当「表」用（大了既费内存又是大 Key） |
| list | quicklist（内部是 listpack 链） | 消息队列（`LPUSH`+`BRPOP`）、最新 N 条 | 按索引随机访问（`LINDEX k 50000` 是 O(N)） |
| set | intset / listpack / hashtable | 去重、标签、共同好友（`SINTER`）、抽奖（`SRANDMEMBER`） | 需要有序（用 zset） |
| zset | listpack / skiplist | 排行榜、延迟队列、按分数范围查 | 只要去重不要排序（set 便宜 40%） |
| bitmap | 就是 string | 签到、活跃用户、**布隆过滤器**（见 Q28） | 稀疏位图（用 set 更省） |

### 三、四个反直觉的点

**1. 内存的悬崖在「每片 512 字段」，不在「总共多少数据」。** 上表：195 个分片（每片 512）只要 **2,010,848 B**，194 个分片（每片 513）要 **7,194,504 B**——数据集完全一样、分片数只差 1，内存差 **3.6 倍**。原因是 listpack 是一整块连续内存、查找靠线性扫描；超过阈值必须转成 hashtable，每个字段都要一个 `dictEntry` + 两个 sds。**设计分片键时，每片字段数必须压到 512 以下**（保守一点取 100~200）。

**2. zset 是最贵的结构，96.2 B/元素，比 list 贵 5.3 倍。** 因为它同时维护一个 dict（member → score）和一个 skiplist（按 score 排序），两边都要存一份 member。如果只需要去重不需要排序，用 set 便宜 40%（55.7 vs 96.2）；如果只需要「有序但可以重」，用 list。

**3. 「用 hash 省内存」在大 hash 上不成立，而且它同时是最典型的大 Key。** 1 个 10 万字段的 hash（71.7 B/条）和不分片的独立 key（72.0 B/条）几乎一样；真正省内存的是**小分片**（64.3 B/条）。省内存和「别造大 Key」在这里方向一致，不是二选一——**分片同时解决两个问题**。

**4. `list-max-listpack-size = -2` 是按「字节」算的，不是按个数。** 实测第 683 个 10 字节元素时切换到 quicklist：683 × 10 = 6,830 B，正好是 8 KB 减掉 listpack 头部开销。正数才是「元素个数」，负数表示「每个 listpack 节点最多多少 KB」（−1=4 KB，−2=8 KB，−3=16 KB，−4=32 KB，−5=64 KB）。

### 四、实战结论

| 场景 | 结论 |
| --- | --- |
| 缓存对象 | 字段少（< 512）且整体小 → 一个 hash；**否则拆成多个 string key**（避免大 Key，也方便单字段更新） |
| 分片设计 | 每片字段数控制在 **100~200**，远低于 512 的悬崖。留余量是因为字段数会增长，一旦越线内存瞬间 3.6 倍且不可逆（删回 512 以下才会转回 listpack） |
| 计数器 | string + `INCR`。别用 hash 存一堆计数器除非要原子地取多个 |
| 排行榜 | zset，`ZREVRANGE` + `ZSCORE`。注意 96 B/成员，千万级成员要几百 MB |
| 去重 | 纯整数且 < 512 个 → intset（极省）；字符串 → set。**只需要「存在性」判断用布隆过滤器（Q28），比 set 省几十倍** |
| 队列 | list + `BRPOP`（阻塞式，比轮询好）。但**没有 ack、没有重试、没有消费组**——要这些用 Stream 或专业 MQ |
| 内存估算 | 别背「1 个 key 多少字节」，按本页的 B/元素 表乘。**估完再乘 1.5 的碎片余量**（这台机器 `mem_fragmentation_ratio` 实测到过 8.69，那是短命大对象造成的，正常长期运行看 1.1~1.5） |
| 上线前 | `redis-cli --bigkeys` 扫一遍，确认没有越线的集合。注意它按**元素个数**排序——`-2` 的 list 元素多但内存小，别被误导 |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| listpack 和 ziplist 什么区别？ | listpack 是 ziplist 的替代品（Redis 7 起 list/hash/zset 的小编码都用它），去掉了 ziplist 的「连锁更新」问题：ziplist 每个节点存前一个节点的长度，改一个可能级联改后面所有；listpack 只存自己的长度 |
| 为什么阈值是「大于」才切换？ | 实测：`hash-max-listpack-value=64`，值长度 64 还是 listpack，65 才转。判据是 `> 阈值`，写配置时别按「≥」估 |
| intset 和 listpack 的 set 有什么区别？ | intset 只存整数、还按大小排序，所以 `SADD` 整数比字符串省得多；但一旦加入非整数成员，整个 set 转成 listpack（< 128）或 hashtable（≥ 128），**转换是单向的**——删掉那个字符串成员也不会转回来 |
| 编码转换可逆吗？ | 不可逆。listpack → hashtable 之后即使删元素回到 512 以下，也不会自动转回 listpack（需要重建 key）。所以「先灌数据再删」不等于「一开始就少灌」 |
| 大 hash 怎么拆？ | 按业务主键取模或哈希（如 `user:info:{id % 100}`），每片控制在 100~200 字段。读单个对象只碰一片，代价是 `HGETALL` 全量要合并 |
| `MEMORY USAGE` 准吗？ | 默认只采样 5 个元素再外推，对 skiplist 这种每节点大小不一的会估歪。实测同一个 300k 成员的 zset：**默认采样连跑 3 次都是 28,852,256**（一模一样——它总是取开头几个元素外推，所以误差是**系统性偏差**，多跑几次消不掉），`SAMPLES 0` 连建 4 次是 31,242,464 ~ 31,251,176（差 0.028%）——**采样版稳定偏低 7.7%**。要准就 `SAMPLES 0` |
| 为什么 string 的 B/元素最大？ | 每个 key 都要一份「key sds + value robj + db 字典的 dictEntry + 过期字典的 dictEntry」。实测 80.0 B/元素里，value 只有 7 字节——**结构开销是数据的 10 倍以上**。这是「key 数量」的真正成本 |
| Stream 呢？ | 本文没实测。场景是「要 ack/消费组/回溯」的队列，内存开销介于 list 和 zset 之间。**本环境未实测，不编数字** |

## Q27. RDB 与 AOF 的丢失窗口

### 结论

RDB 的丢失窗口**不是一个时间，是一个条件**。`save` 的两个判据是「**且**」：

```
   save 60 10000
        │
        ├── 距上次成功存盘 >= 60 秒 ──┐
        │                            ├── 两个都满足，BGSAVE 才触发
        └── 累计写入 >= 10000 次 ────┘
```

实测：`save 60 10000` 下灌 12,000 条（写次数早就够了）然后 kill -9，**丢光 12,000 条**——因为只过了 1 秒。`rdb_changes_since_last_save` 停在 12000 没被清零，证明 BGSAVE 压根没启动。

AOF `everysec` 在 **kill -9** 下**一条不丢**（实测 2000/2000 全在，连 `appendfsync no` 的 30,000 条也全在）。原因是 `write()` 早就把数据交给内核 page cache 了，`kill -9` 只杀进程、杀不掉内核里的页。**所以「everysec 有 1 秒丢失窗口」这句话，在本环境用 kill -9 是验不出来的**——它只在断电 / 内核崩溃时成立。

### 一、崩在哪，决定了丢什么

```
  RDB 模式
  ├─ 写 2000 条 ────► 内存 + dirty 计数 ────►[BGSAVE 触发]────► dump.rdb
  │                        │                     ▲
  │                        │                     │ 未触发就是空的
  │                   ✗ kill -9 在这里            │
  │                   → 内存里的 2000 条全丢，磁盘上还是上一次的 rdb
  │
  └─ docker stop（SIGTERM）────► 优雅关闭，主动存一次 ────► 一条不丢

  AOF 模式
  ├─ 写 ──► 主线程 append 到 aof_buf ──► write() ──► 内核 page cache ──► fsync() ──► 磁盘
  │                                          │              │              │
  │                                     ✗ kill -9 在这      │         everysec：每秒一次
  │                                     → 数据还在内核里，   │         always：每条都做
  │                                       重启能读到          │
  │                                                        ✗ 断电 / 内核 panic 在这
  │                                                        → page cache 没了，这段全丢
```

**`kill -9` 和「断电」不是一回事**。本文所有「崩溃」都用 `docker kill`（= SIGKILL），它验证的是「进程级崩溃」；**「断电级崩溃」本环境无法复现**。

### 二、实测（Redis 7.4.11）

脚本：`../bench/redis/02-persistence.sh`（**必须在宿主机跑**：脚本内部要 `docker run` / `kill` / `start`）

为什么不用 `learn-redis` 做实验：它的 `redis.conf` 是 `:ro` 挂载，`CONFIG REWRITE` 写不进去，容器重启后 `appendonly` 又回到配置文件里的值——会把「配置没生效」误读成「AOF 丢了数据」。脚本改用同一个镜像起一个一次性容器，启动参数就是重启后的配置，跑完 `docker rm -f`。

> **坑**：`docker exec` 不加 `-i` 时不接 stdin，`redis-cli --pipe` 会**静默写入 0 条**。可复现：
>
> ```
> $ printf 'SET k 1\n' | docker exec learn-redis redis-cli --pipe      # 没有 -i
>   All data transferred. Waiting for the last reply...
>   Last reply received from server.
>   errors: 0, replies: 0        ← 输出看起来完全成功，但 replies=0
>   EXISTS k → 0                 ← 一个字都没写进去
> $ printf 'SET k 1\n' | docker exec -i learn-redis redis-cli --pipe   # 加上 -i
>   errors: 0, replies: 1
>   EXISTS k → 1
> ```
>
> 第一版脚本就是这么翻车的（每个场景都报 DBSIZE=0，看上去像「RDB 把数据全丢了」）。所以脚本第 0 节专门先验证基线。

| # | 场景 | 写入量 | 怎么停 | **丢了多少** |
| --- | --- | ---: | --- | --- |
| 0 | 基线：确认 `--pipe` 真写进去了 | 2,000 | — | DBSIZE=2000 ✓ |
| A | RDB，`save 3600 1`（拉长到 1 小时） | 2,000 | `kill -9` | **丢 2,000 / 2,000** |
| B | RDB，默认 `save 60 10000` | 2,000 | `kill -9` | **丢 2,000 / 2,000** |
| C | RDB，`save 60 10000`，灌 12,000 条（写次数够） | 12,000 | 1 秒后 `kill -9` | **丢 12,000 / 12,000** |
| C2 | RDB，把 `save` 调密到 `1 1` | 12,000 | 1.5 秒后 `kill -9` | **丢 0 / 12,000** |
| D | RDB，`save 3600 1`，**优雅停止** | 2,000 | `docker stop`（SIGTERM） | **丢 0 / 2,000** |
| E | AOF `appendfsync everysec` | 2,000 | `kill -9` | **丢 0 / 2,000** |
| F | AOF `appendfsync always` | 2,000 | `kill -9` | **丢 0 / 2,000** |
| H | AOF `appendfsync no`（最"不安全"的模式） | 30,000 | `kill -9` | **丢 0 / 30,000** |

**场景 C 的关键证据**：

```
  写入后 DBSIZE=12000  rdb_changes_since_last_save=12000
  1 秒后 rdb_changes_since_last_save=12000   ← 没被清零，说明 BGSAVE 压根没触发
```

**场景 C2 的对照**（同样 12,000 条，`save 1 1`）：

```
  写入后 DBSIZE=12000  rdb_changes_since_last_save=0（被 BGSAVE 清零了）
  重启后 DBSIZE=12000   ← 丢 0 / 12000
```

**场景 E 的关键证据**（AOF 文件在崩溃那一刻的状态）：

```
  写入后 DBSIZE=2000
    aof_last_write_status:ok
    aof_current_size:67809
    aof_pending_bio_fsync:0
    aof_delayed_fsync:0
  --- 崩溃瞬间磁盘上的 AOF 文件里有没有最后那条 k2000 ---
      grep 命中行数: 1
      AOF 文件大小:  appendonly.aof.1.incr.aof(67809 B)
      ↑ everysec 的 fsync 每秒才跑一次，这一刻它还没跑；但数据已经在文件里了：
        write() 早就把数据交给内核 page cache，kill -9 只杀进程，杀不掉内核里的页
```

**场景 G：三种 `appendfsync` 的写吞吐**（跑了 3 次，本环境的噪声底大约 ±20%）

| `appendfsync` | 第 1 次 SET rps / p50 | 第 2 次 | 第 3 次 |
| --- | ---: | ---: | ---: |
| `everysec` | 31,201 / 0.831 ms | 33,333 / 0.863 ms | 38,685 / 0.743 ms |
| `always` | **8,150 / 5.863 ms** | **8,003 / 5.823 ms** | **12,788 / 3.767 ms** |
| `no` | 21,930 / 1.271 ms | 37,594 / 0.807 ms | 43,103 / 0.679 ms |

`always` 三次都掉到 `everysec` 的 **1/3 ~ 1/4**，p50 从 0.7~0.9 ms 涨到 3.8~5.9 ms——**这是每条命令一次 fsync 的真实代价，方向稳定**。而 **`no` 和 `everysec` 三次跑不一致**（`no` 分别 21,930 / 37,594 / 43,103），本环境测不出稳定结论：两者本来就只差「谁来决定 fsync 时机」，没有每条命令的固定开销。

### 三、四个反直觉的点

**1. `save` 的两个条件是「且」，不是「或」。** 这是最容易踩的坑：以为「写了 10,000 次就会存盘」，于是配 `save 60 10000` 就放心了——结果低峰期（每秒写 10 次）要攒 **1000 秒**才能满足 10,000 次，这段时间全在裸奔。实测场景 C 就是这个：写够了次数，但时间没到，一条不存。

**2. `kill -9` 丢不掉 AOF 数据，所以「everysec 会丢 1 秒」在本环境验不出来。** `write()` 和 `fsync()` 是两件事：前者把数据交给内核 page cache（进程一调用就完成），后者才落盘。`kill -9` 杀掉的是进程，page cache 归内核管，重启后照样读得到。**AOF 的 1 秒窗口只在断电 / 内核 panic 时存在——这块未实测，别把「kill -9 不丢」当成「everysec 安全」。**

**3. `appendfsync no` 一条没丢，还写了 30,000 条。** 「no」不是「不同步」，是「交给内核决定什么时候刷」（Linux 默认约 30 秒）。进程崩溃场景下它和 `everysec` 一样安全；只有断电才会丢，而且丢的可能比 `everysec` 还多。

**4. 丢失与否，更大程度取决于「怎么停」而不是「怎么配」。** 场景 A 和场景 D 用的是**完全相同的配置**（`save 3600 1`），A 丢光、D 一条不丢——唯一区别是 `kill -9` vs `docker stop`。Redis 收到 SIGTERM 会走 `prepareForShutdown()` 主动存一次盘。**K8s 里 Pod 被删是 SIGTERM，`kill -9` 才是 SIGKILL**，这个区别在容器环境里经常被忽略。

### 四、实战结论

| 场景 | 结论 |
| --- | --- |
| 只用 RDB | **丢失窗口不是你能算出来的**，它取决于写入密度。低频业务必须把 `save` 改成按时间触发（如 `save 900 1 300 10 60 10000`，且第一条要满足「900 秒内有 1 次写」——低频也能触发） |
| 要 RDB 也要 AOF | Redis 4+ 支持混合持久化（`aof-use-rdb-preamble yes`，7 默认开）：AOF 文件前半是 RDB 快照、后半是增量命令。**重启快、增量全**，是推荐配置 |
| `appendfsync` 怎么选 | 默认 `everysec`。实测 `always` 掉到 1/3~1/4 吞吐、p50 涨 5~7 倍，**绝大多数业务不值得**。`no` 不建议——省下的那点性能换来的不确定性不划算（三次跑还没跑出稳定优势） |
| 能不能一条不丢 | **不能靠 Redis 单机做到**。要强一致得走 `WAIT`（同步复制，代价是延迟）+ 主从，或者干脆不把 Redis 当存储。**任何「Redis 持久化 = 不丢数据」的说法都是错的** |
| 掉电安全 | `everysec` 在断电时最多丢 1 秒。**这一条本环境未实测**（无法复现断电），按官方文档口径 |
| 重启慢 | 先看 AOF 大小。`BGREWRITEAOF` 能压缩，但**重写期间的阻塞本环境未实测**。混合持久化能显著缩短重启时间（直接加载 RDB 部分） |
| 容量规划 | AOF 会比数据本身大（每个写命令都存文本），实测 30,000 条小 SET 的 AOF 是 **1,087,988 B**（约 36 B/条）。`auto-aof-rewrite-percentage` 默认 100（翻倍就重写） |
| 上线前必做 | **实际 kill -9 一次**，量重启耗时和丢失量。别信配置，信实验 |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| RDB 和 AOF 能同时开吗？ | 能，而且推荐。重启时**优先用 AOF**（`aof-use-rdb-preamble` 让它包含 RDB 部分）。`appendonly yes` 时 RDB 仍可按 `save` 规则生成，用于备份/从库同步 |
| BGSAVE 是 fork 出来的，fork 会阻塞吗？ | 会，但很短（复制页表，与内存大小成正比）。真正的风险是 COW：fork 后如果写量大，页被复制，内存可能翻倍。**具体阻塞时长本环境未实测** |
| AOF 重写期间的新写怎么办？ | 重写子进程基于 fork 时刻的快照，期间新写命令同时追加到「重写缓冲区」，子进程完成后把缓冲区追加进去。所以不会丢 |
| 为什么 AOF 是多个文件？ | Redis 7 的多 part AOF：一个 manifest + 一个 base（RDB 或 AOF）+ 若干 incr。实测目录里是 `appendonly.aof.1.incr.aof`。好处是重写不用「先写临时文件再 rename」 |
| `no-appendfsync-on-rewrite` 是什么？ | 重写期间主线程的 fsync 会让 `always`/`everysec` 卡住，这个开关让重写期间不 fsync（安全性降到 `no` 的水平）。**收益未实测** |
| 主从复制能救吗？ | 复制是异步的，主挂了从可能还没收到。`WAIT numreplicas timeout` 可以阻塞等从库确认，但每条命令都等会拖垮吞吐。**未实测** |
| RDB 文件能直接读吗？ | 不能，是二进制格式。要分析用 `redis-check-rdb`。AOF 是文本命令，能直接看（实测 `grep k2000` 命中，这也是本文验证「数据已在文件里」的手段） |
| `aof_last_write_status` / `aof_delayed_fsync` 看什么？ | 前者是 `ok`/`err`，磁盘满时变 `err` 且 Redis 会拒绝写（`stop-writes-on-bgsave-error`）；后者是「因为正在 fsync 而被推迟的后台 fsync 次数」，持续增长说明磁盘跟不上 |

## Q28. 缓存穿透、击穿、雪崩

### 结论

三者经常被混在一起讲，但**解法完全不同**，因为它们的失效机理不同：

| | 打的是什么 | 关键量 | 解法 |
| --- | --- | --- | --- |
| **穿透** | **不存在**的 key | 回源次数 | 布隆过滤器 / 空值缓存 |
| **击穿** | **一个**刚失效的热 key | 重建期间的并发数 | 互斥重建 / 逻辑过期 |
| **雪崩** | **一批**同时失效的 key | 瞬时回源 QPS | TTL 打散 / 多级缓存 |

**穿透的实测结论**：空值缓存只对「反复打同一个不存在的 id」有效。攻击者每次换新 id 时，1,000 次请求**回源 1,000 次**，还倒贴 1,000 个 Redis key（72,000 字节）——**缓存本身成了被攻击面**。布隆过滤器把同样 1,000 次攻击压到 **0 次回源**（固定 id）和 **9 次**（换新 id，9 次是误判），位图只占 **1,328 字节**。代价是误判率完全由位图大小决定，实测 4 bit/元素 → **15.26%**，20 bit/元素 → **0.015%**。

**击穿**：50 个并发进程同时打一个刚失效的热 key，无防护回源 **50 次**，互斥重建回源 **1 次**——**回源量差 50 倍**。

**雪崩**：500 个 key 同一时刻失效，回源尖峰 **336 次/200ms**（≈1,680 q/s）；TTL 打散后峰值 **85 次/200ms**（≈425 q/s），尖峰被摊平。

### 一、请求路径和三种失效模式

```
   ┌─────────┐   GET   ┌────────┐  miss   ┌──────────┐
   │  请求   ├────────►│ Redis  ├────────►│  MySQL   │
   └─────────┘         └────────┘         └──────────┘
        │                   │                   ▲
        │                   │ hit               │
        │                   ▼                   │
        │              ┌─────────┐              │
        └─────────────►│  返回   │              │
                       └─────────┘              │
                                              │
   ① 穿透：请求的 key 数据库里根本没有 ─────────┘  每次都走到底
   ② 击穿：一个热 key 刚好过期，N 个请求同时走到这里
   ③ 雪崩：一批 key 同一时刻过期，N×M 个请求同时走到这里
           └─ 三者都表现为「回源量突增」，但只有①是「数据不存在」

   ┌────────────────────────────────────────────────────────┐
   │ 布隆过滤器挡在 Redis 前面：                              │
   │                                                        │
   │   请求 ──► [布隆过滤器] ──"一定不存在"──► 直接返回空      │
   │                 │                                      │
   │                 └──"可能存在"──► [Redis] ──► [MySQL]    │
   │                                                        │
   │   单向：说「不存在」一定准；说「存在」可能是误判          │
   └────────────────────────────────────────────────────────┘
```

### 二、实测（Redis 7.4.11 + MySQL 8.4.11 + PHP 8.4.25）

脚本：`../bench/redis/q28-cache.php`（`docker exec learn-php php /app/bench/redis/q28-cache.php <setup|penetration|breakdown|avalanche>`）

**回源次数怎么保证是真的**：读 MySQL 的 `SHOW SESSION STATUS LIKE 'Com_select'`，这是**服务端会话计数器**，PHP 侧改不了。不能用 `GLOBAL`——这台 MySQL 上还有别的会话在跑，实测 GLOBAL 空转噪声 **1,200~4,300 q/s**，任何差值都被淹掉。子进程各自读自己的会话计数，再 `INCRBY` 汇总到 Redis，两边对不上就说明实验有问题。

后端表：`q28_cache.users`，1,000 行，主键 `id`。**击穿那节**的回源用 `SLOW_MS = 50` 模拟慢查询（真实主键查询太快，重建窗口撑不开）；**穿透那节不用**——它要测的是「被打多少次」，回源越快越能看清 1,000 次全打到底。

**1. 穿透**（1,000 次请求，目标 id 全都不存在）

| # | 做法 | 回源次数 | 耗时 | 附加成本 |
| --- | --- | ---: | ---: | --- |
| 1 | 固定 id=999999，**无防护** | **1,000** | 0.284 s（3,519 q/s） | — |
| 2 | 固定 id=999999，**空值缓存** | **1** | 0.105 s | 1 个 key |
| 3 | **每次换新 id**，空值缓存 | **1,000** | 0.579 s | **1,000 个 key / 72,000 B** |
| 4 | 固定 id，**布隆过滤器**（10,000 bit / k=7） | **0** | 0.101 s | 位图 1,328 B |
| 5 | 换新 id，布隆过滤器 | **9**（误判） | 0.198 s | 位图 1,328 B |

第 3 行是重点：**空值缓存对「换 id」的攻击完全无效**，而且攻击者写进去的 1,000 个 key 要占 72,000 字节——**缓存成了放大器**；第 3 行还比第 1 行**更慢**（0.579 s vs 0.284 s），因为多付了 1,000 次 `SET` 的钱。

**2. 布隆过滤器误判率实测**（n=1,000 个真实 id，拿 20,000 个不存在的 id 探）

| 位图 bit | k | bit/元素 | **实测误判率** | MEMORY USAGE |
| ---: | ---: | ---: | ---: | ---: |
| 4,000 | 3 | 4.0 | **15.260%** | 568 B |
| 8,000 | 6 | 8.0 | **2.170%** | 1,080 B |
| 10,000 | 7 | 10.0 | **0.935%** | 1,336 B |
| 20,000 | 14 | 20.0 | **0.015%** | 2,616 B |

（每档只探了 20,000 个样本，实测值有抖动，不是理论值。实现是 Redis 位图 `SETBIT` + `crc32` 双哈希模拟 k 个位置。）

**3. 击穿**（50 个并发进程同时请求一个刚失效的热 key）

| 做法 | 回源次数 | 全部跑完耗时 |
| --- | ---: | ---: |
| 无防护 | **50** | 2.188 s |
| **互斥重建**（`SET NX PX` 抢到锁的才回源） | **1** | 1.853 s |

**这里只有「回源次数」这一列可信，耗时那列不是。** 两个数都被「fork 50 个 PHP 进程 + 每个重连 Redis 和 MySQL」的开销支配，跟被测的东西无关（互斥重建反而更快，就是因为 49 个进程只轮询不等数据库）。**回源 50 次 vs 1 次才是结论**——这 50 次打在真实 MySQL 上，每一次都是那 50 ms 的慢查询。

**4. 雪崩**（500 个缓存 key，10 个并发客户端，观察 6,000 ms）

| TTL 策略 | 总回源 | 峰值 | 折算 |
| --- | ---: | ---: | ---: |
| 同一时刻失效（`TTL=3s`） | 1,022 | **336 次/200ms** | ≈1,680 q/s |
| TTL 打散（`3s + rand(0,3)`） | 619 | **85 次/200ms** | ≈425 q/s |

每 200 ms 的回源数（前 15 个桶），尖峰形状一目了然：

```
  同一时刻失效:  0  0  0  176  336    2  0  0  0   0   0   0   0   0   0
                          └────┬────┘
                        两个桶吃掉 512 次

  TTL 打散:      0  0  0   0   0   69  69  0  0  0  71  53   0   0   0
                          └──────── 摊成 4 个矮峰 ────────┘
```

### 三、四个反直觉的点

**1. 空值缓存防不住「换 key」的攻击，还会变成攻击者的写入放大器。** 实测：换新 id 打 1,000 次，回源 1,000 次一次没挡住；同时 Redis 里多了 1,000 个 key、72,000 字节。**如果空值不设 TTL，这些垃圾会永久占内存**；就算设了 TTL，攻击者只要持续换 id 就能持续占用。**空值缓存只适合「有明确 ID 空间上限」的场景**（比如只允许 `id ∈ [1, 10^7]`，且非法 ID 会被前置校验拦掉）。

**2. 布隆过滤器的内存和误判率是指数关系，不是线性。** 实测：4 bit/元素 → 15.26%，20 bit/元素 → 0.015%——**内存 5 倍，误判率降到 1/1000**。所以「用多少内存」是设计决策，不该拍脑袋。经验值：1% 误判约需 **10 bit/元素**（实测 0.935%），0.1% 约需 14 bit/元素。

**3. 布隆过滤器只能「挡不存在」，不能「挡存在」——它永远不会漏掉真数据，只会多放一些假数据进来。** 实测第 5 行：换新 id 攻击 1,000 次，误判放进来 9 次（0.9%，与 10 bit/元素的理论值吻合）。这 9 次会走到 Redis（未命中）再走到 MySQL。**误判的代价是一次多余的查询，不是错误结果**——这就是它能用的原因。

**4. 雪崩的「打散」只能摊平，不能消除。** 实测尖峰从 336 降到 85（4.0 倍），总回源从 1,022 降到 619——**总量还是那么多，只是不再集中**。如果后端连摊平后的 425 q/s 都扛不住，打散救不了你，得靠多级缓存或预热。

### 四、实战结论

| 场景 | 结论 |
| --- | --- |
| 穿透防护 | **优先布隆过滤器**（内存小、挡住换 key 攻击）；空值缓存只作为补充，且**必须设短 TTL**（如 60 s）。两者可以叠加 |
| 布隆过滤器选型 | 本环境用的是手写 `SETBIT` + `crc32`。生产建议用 **RedisBloom 模块**（`BF.ADD`/`BF.EXISTS`/`BF.RESERVE`，支持自动扩容和 `BF.INFO` 查误判率）——**RedisBloom 本环境未实测** |
| 布隆过滤器的更新 | **不支持删除**（删一个元素会影响其他元素的位）。数据会删的场景要用 Counting Bloom 或 Cuckoo Filter，或者定期重建。**重建期间的空窗本环境未实测** |
| 空值怎么存 | 存一个不可能与真实值冲突的哨兵（如 `"__NULL__"`），**不要存 `null` 或空字符串**——前者 PHP 侧 `get()` 返回 `false` 分不清「miss」和「值为 null」，后者和真实空值混淆 |
| 击穿防护 | 单机用 `SET NX PX` 互斥重建（见 Q30 的正确写法）；要求「永不阻塞」用逻辑过期（value 里带过期时间，过期后返回旧值 + 异步重建） |
| 热 key 的额外手段 | 本地缓存（APCu / Swoole Table）挡住绝大部分读，但**一致性变难**；或把热 key 复制成 N 份加随机后缀分散到不同实例（**本环境无 Cluster，未实测**） |
| 雪崩防护 | TTL 加随机抖动是最低成本的手段，**本文实测有效**（用的是 `TTL=3s + rand(0,3)`，即抖动幅度等于基准 TTL；生产上取 `base + rand(0, base*0.2)` 就够，不必这么激进）。此外：多级缓存、缓存预热、熔断降级（后端扛不住时直接返回兜底值） |
| 监控 | 盯三个数：**缓存命中率**（跌了就是穿透/雪崩）、**回源 QPS**（突增就是击穿/雪崩）、**Redis 的 key 数量增长速率**（异常增长就是被写入放大） |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| 布隆过滤器和 `SET` 去重有什么区别？ | 内存差几十倍（实测 10 bit/元素 = 1.25 B/元素，set 是 55.7 B/元素），代价是误判和不能删除。**判断「存在性」且能接受误判时用布隆，要精确用 set** |
| 布隆过滤器为什么不能删除？ | 一个元素对应 k 个位，这些位是多个元素共享的。把某元素的 k 个位清零，会连带把其他元素的位清掉，导致**假阴性**——而假阴性意味着「真的数据被判定为不存在」，这是不能接受的错误 |
| 缓存预热怎么做？ | 上线前或低峰期用脚本把热点数据灌进 Redis（`MULTI`/pipeline 批量 `SET`）。关键是**预热数据也要带随机 TTL**，否则预热完又变成同时失效 |
| 「逻辑过期」是什么？ | value 里存 `{data, expire_at}`，Redis 的 TTL 设成永不过期（或不设）。读到 `expire_at` 已过就返回旧数据，同时异步（抢锁）重建。好处是**永不阻塞请求**，坏处是**会返回过期数据**——适合能容忍短暂不一致的场景 |
| 互斥重建的锁挂了怎么办？ | 必须给锁设过期时间（见 Q30）。锁的 TTL 要**大于重建耗时**，否则重建还没完锁就没了，第二批请求又会进来重建 |
| 多级缓存的一致性怎么保证？ | 本地缓存（进程内）无法被 Redis 的删除操作感知到，只能靠短 TTL（秒级）或广播失效。**本环境未实测**，属于架构层面的取舍 |
| 命中率多少算正常？ | 没有普适数字，取决于业务。**能说的是：命中率要看趋势不看绝对值**——突然从 95% 掉到 80%，比一直是 80% 危险得多 |
| 布隆过滤器的位图多大合适？ | `m = -n·ln(p) / (ln2)²`，n 是预估元素数、p 是目标误判率。1 亿元素、1% 误判约需 958 Mbit ≈ 114 MB。**这个公式本环境未逐点验证**，只在 1,000 元素 / 4 种位图规模上量了误判率，实测值与公式吻合（10 bit/元素 → 实测 0.935%，公式 0.82%） |

## Q29. 缓存与数据库的一致性

### 结论

「先删缓存还是先更新库」这个问法本身问错了。真正决定脏数据率的是**窗口宽度**，而窗口宽度是可以量的。实测（MySQL 8.4.11，`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` + `log_bin=1`）：

| 操作 | p50 | p99 |
| --- | ---: | ---: |
| 读侧完整回填（`GET` miss + `SELECT` + `SET`） | 0.655 ms | 1.038 ms |
| 写侧单行 `UPDATE`（走主键） | 2.955 ms | 6.883 ms |
| 写侧 200 行 `UPDATE`（全表扫，无可用索引） | 5.700 ms | 22.354 ms |
| 写侧 3 条 `UPDATE` 一个事务 | 8.598 ms | 15.870 ms |
| 写侧 `DEL` 缓存一个来回 | 0.103 ms | 0.196 ms |

两种顺序的窗口：

```
  ① 先删缓存            W: DEL ──────────────────────────► UPDATE 提交
                          │                                    │
                          └────────── 窗口 = UPDATE 耗时 ──────┘
                              （3.0 ~ 8.6 ms，读请求在这期间回填旧值）

  ② 先更新库再删缓存     W: ──── UPDATE 提交 ── DEL ──►  （窗口关闭）
                        R: GET miss ── SELECT 旧值 ────────────── SET 旧值
                                                                    ▲
                          窗口 = 回填耗时 − (UPDATE + DEL)          │
                              p50: 0.655 − (2.955+0.103) = −2.4 ms   │
                              p99: 1.038 − (6.883+0.196) = −6.0 ms   │
                              → 本环境两次都是负数：回填比「更新+删」快
```

**两个窗口的符号不一样**：①的窗口恒为正（就是 `UPDATE` 本身），②的窗口在**本环境是负数**（回填只要 0.66 ms，而「更新+删」要 3.06 ms）。所以 4,000 ms 压力测试（1 写 + 20 读）的差距非常悬殊：

| 顺序 | 写次数 | 读次数 | **留下脏数据的写** |
| --- | ---: | ---: | ---: |
| 先删缓存 | 470 | 68,170 | **444 次 = 94.47%** |
| 先更新库再删 | 530 | 66,896 | **1 次 = 0.19%** |

**「先更新库再删」好约 500 倍，但不是零。** 而且②的负数窗口不是保证——**只要回填变慢（序列化大对象、GC 停顿、读走从库），窗口就会翻正**。所以下面用一个人为拖慢的回填，演示它翻正的样子。

延迟双删（600 ms 后补一刀）在确定性交错里确实修好了：终局缓存为空，下一次读拿到新值。

### 一、竞态长什么样

用**绝对时刻**调度两个真实进程（不是「先跑 A 再 sleep 再跑 B」），确定的交错如下：

```
  先删缓存（del-first）—— 实测会脏

    W  t=   0ms  DEL 缓存
    R  t=  20ms  GET 缓存 → miss（刚被 W 删掉）
    R  t=  25ms  SELECT → v=0          ← 读到旧值
    R  t= 230ms  SET 缓存 = 0          ← 回填旧值
    W  t= 300ms  UPDATE item SET v=100 (耗时 18.25ms)
                 │
                 └─ 终局：DB.v=100  cache=0   ← 脏，而且不会自愈

  先更新库再删（update-first）—— 把回填人为拖慢到 250ms 时也会脏

    R  t=   0ms  GET 缓存 → miss
    R  t=   5ms  SELECT → v=0          ← 读发生在 UPDATE 之前，拿到旧值
    W  t= 100ms  UPDATE item SET v=100
    W  t= 110ms  DEL 缓存
    R  t= 250ms  SET 缓存 = 0（模拟回填慢：序列化 / GC / 网络抖动）
                 │
                 └─ 终局：DB.v=100  cache=0   ← 脏
                     （注意：这是把回填从 0.66ms 拖到 250ms 才造出来的。
                       本环境自然状态下窗口是负的，见上表 0.19%）

  延迟双删（del-first-double）—— 实测修好了

    W  t=   0ms  DEL 缓存（第一次）
    R  t=  20ms  GET 缓存 → miss
    R  t=  25ms  SELECT → v=0
    R  t= 230ms  SET 缓存 = 0
    W  t= 300ms  UPDATE item SET v=100
    W  t= 900ms  DEL 缓存（第二次，延迟 600ms）  ← 把 t=230ms 那次回填清掉
                 │
                 └─ 终局：cache=(空) → 下一次读拿到 100，一致
```

关键点：**脏数据不会自愈**。`cache=0` 这个坏值会一直活到 TTL 到期（本文设 30 s），期间所有读都拿到旧值。脚本里紧接着做了一次「正常读」，结果仍然是脏的——因为缓存里有值，根本不会回源。

### 二、实测（MySQL 8.4.11 + Redis 7.4.11 + PHP 8.4.25）

脚本：`../bench/redis/q29-consistency.php`（`docker exec learn-php php /app/bench/redis/q29-consistency.php <setup|window|race <order>|stress <order>>`）

表：`q28_cache.item`（1 行）+ `q28_cache.item_rows`（2,000 行，`city` 字段**故意不加索引**，用来模拟「一次业务更新影响多行」）。

**为什么单行 UPDATE 要 2.96 ms**：本环境 MySQL 开了 `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1` + `log_bin=1`，**每次提交都要 fsync**。这个数是环境的产物，不是 MySQL 的常态；但它同时解释了为什么「先删缓存」的窗口这么宽。

**压力测试的脏数据判定**（写侧）：写请求做完 `UPDATE` + `DEL` 之后 **2 ms** 再 `GET` 缓存，如果缓存里非空且 < 刚写入的版本号，就判定为「有个读请求把旧值回填进去了，且这次 `DEL` 没能清掉」。这是**下界**——回填发生在检查之后的那些没算进来。

### 三、五个反直觉的点

**1. 「先更新库再删缓存」本环境窗口是负的，所以它脏得极少（0.19%）——但这不是保证，是这台机器的巧合。** 窗口 = 回填耗时 − (UPDATE + DEL)。实测 p99 下是 1.038 − 7.079 = **−6.0 ms**，回填比「更新+删」快 6 毫秒。**只要回填变慢——序列化一个大对象、一次 GC 停顿、回源走从库多一跳——这 6 毫秒就被吃掉，窗口翻正，脏数据立刻回来。** 所以正确的说法是「先更新库再删，在本环境实测 0.19%，且它对回填延迟的余量只有 6 ms」，而不是「它几乎不会出问题」。

**2. 先删缓存的窗口是「整个 UPDATE 耗时」，而且必然为正。** 实测 94.47% 的写留下脏数据。因为窗口从 `DEL` 一直开到 `UPDATE` 提交，这段时间里**任何一个读请求回填进去的都是旧值**——不需要任何时序巧合。而且窗口宽度正比于业务复杂度：单行 UPDATE 是 2.96 ms，事务里改 3 条就是 8.60 ms，全表扫 200 行是 5.70 ms。

**3. 延迟双删的「延迟」是一个赌注，不是参数。** 实测 600 ms 的延迟能修好那个交错，但那是**因为我把回填人为拖到了 230 ms**。真实系统里回填耗时是长尾分布，**延迟设小了没盖住，设大了脏数据窗口就长**。而且第二次 `DEL` 之后如果还有更慢的读在回填，照样脏——**它降低概率，不消除问题**。

**4. 脏数据不会自愈，而且它活得比你想的久。** 缓存的 TTL 是 30 s，意味着这个坏值会**挡住 30 秒内的所有读**——每次读都命中缓存拿到旧值，压根不会去查库。脚本里紧接着做的那次「正常读」验证了这一点：`cache=0 DB=100`，仍然脏。**TTL 是所有一致性方案的最后一道防线，而它的长度就是「你能容忍多久不一致」的直接答案。**

**5. 「缓存和数据库强一致」在缓存旁路模式下做不到。** 要强一致只能用「读写都走同一把锁」（性能垮掉）或让缓存成为唯一数据源（就不是缓存了）。**工程上的目标是「最终一致 + 窗口尽量小」**，所以真正该做的不是纠结顺序，而是：给缓存设短 TTL 兜底、把回填路径做快、以及**接受「TTL 期间可能读到旧值」这个业务事实**。

### 四、实战结论

| 场景 | 结论 |
| --- | --- |
| 顺序选哪个 | **先更新库，再删缓存**。实测脏数据率 0.19% vs 94.47%。绝对不要「先删缓存再更新库」 |
| 为什么是「删」不是「更新」 | 更新缓存要处理并发写的覆盖问题（两个写请求的缓存更新可能乱序），删除是幂等的。**删除的代价是一次 miss，更新的代价是一次错误** |
| 要更强一致 | 延迟双删（延迟 ≈ 读回填的 p99 × 2）。但要知道它是概率手段，**不能当成保证** |
| TTL 兜底 | **一定要设**。它是所有一致性方案失效时的最后一道防线。本文设 30 s，实际业务按「能容忍多久不一致」定 |
| 延迟双删的延迟怎么定 | 先量你系统的回填 p99（本文是 1.038 ms），延迟取 **几十~几百毫秒**。**本文只验证了 600 ms 能修好一个确定交错，没扫参数** |
| 写多读少 | 考虑「删除 + 不缓存」：写的时候直接 `DEL`，读的时候如果 miss 就回源但**不写回**（或写回很短 TTL）。避免无谓的缓存写 |
| 读多写少 | 缓存旁路 + TTL 抖动的标准做法。核心是把**回填路径做快**（回填越慢窗口越宽） |
| 更强方案 | 订阅 MySQL binlog（Canal / Debezium）异步失效缓存。**本环境未实测**——它能把窗口压到毫秒级，但引入了新的组件和延迟 |
| 上线前必做 | 量三个数：**回填 p99**、**写操作 p99**、**缓存 TTL**。前两个决定窗口宽度，TTL 决定脏数据最长活多久 |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| 为什么「先删缓存」这么流行？ | 因为它简单、看起来合理（「先清干净再写」）。但它的窗口是**整个 UPDATE 耗时**且必然为正，实测 94.47% 的写会留下脏数据——**这个方案在任何环境下都不该用**，差别只是事故什么时候来 |
| 延迟双删的第二次删除失败了怎么办？ | 需要重试（消息队列 / 定时任务补偿）。本文未实现重试，只验证了「成功删除时能修好」 |
| 主从架构下有什么额外问题？ | 主从复制是异步的：先更新主库再删缓存，如果缓存紧接着被回源且读的是从库（还没同步），会回填旧值。**需要「写后读主库」或等主从同步**。本环境无主从，未实测 |
| 能不能用 `SET` 代替 `DEL`？ | 能，但要处理两个写的乱序：A 写 v=1、B 写 v=2，如果 B 的缓存更新先落地、A 的后落地，缓存就永久是 v=1。修法是「只在新值大于旧值时更新」（需要版本号）或加锁。**所以默认用 `DEL`** |
| 缓存里存的是什么？ | 本文存的是 `v` 的字符串。真实业务存 JSON/序列化对象，回填耗时更长——**回填越慢，「更新库再删」的窗口越容易变正**，这点在设计时要算进去 |
| 读写分离的从库延迟算进去吗？ | 算。读回源如果走从库，回填的可能是更旧的值。这时「更新库再删」的窗口 = 回填耗时 + 主从延迟 − (UPDATE + DEL)，更容易变正 |
| 有没有「完全不脏」的方案？ | 有：把缓存当唯一数据源（Redis 持久化做存储），或者读也加锁。前者放弃了 MySQL 的角色，后者放弃了性能。**通用场景下不存在** |
| 双删的「延迟」用定时任务还是 MQ？ | 简单场景用 `sleep`（会占住 PHP 进程，不推荐）；生产用延迟消息（RabbitMQ 死信 / Redis zset 延迟队列）。**本环境未实测延迟队列方案** |

## Q30. Redis 分布式锁

### 结论

`SET NX PX` 只是起点，三个洞必须补：

**1. 误删别人的锁。** 实测时序：A 在 t=30 ms 加锁（`PX 800`），B 在 t=100 ms 抢失败，A 的锁在 t=830 ms 过期、B 在 t=900 ms 抢到，A 在 t=1500 ms 收工执行 `DEL`——**删掉的是 B 的锁**，C 随即在 t=1600 ms 拿到锁。**B 和 C 同时认为自己在临界区。** 用 Lua 校验 value 之后，同一时序下 A「发现自己已经不是持有者，什么都没删」，C 在 t=1600 ms 加锁**失败**，互斥从头到尾成立。

**2. 过期时间不够。** 锁 `PX 800` 但活要干 4,200 ms，不续期的话 A 在 **t=814 ms** 就发现锁不在自己手里，B 在 **t=822 ms** 抢到——**互斥彻底破坏**。加看门狗自动续期后，A 全程持有 4,200 ms 一刻没丢，B 直到 **t=4222 ms** 才抢到（晚于 A 释放 4213 ms）。

**3. 续期也必须校验持有者**，否则会续到别人的锁上（本文的实现用 Lua 做了校验）。

`SET NX PX` 相比无锁的效果：20 个进程 × 100 次「读-改-写」，无锁**期望 2,000 实际 109（丢 94.5%）**，加锁**期望 2,000 实际 2,000（丢 0）**。

### 一、误删是怎么发生的

```
  t(ms)   A（持锁者，活要干 1500ms）      B（第二个）            C（第三个）
    │
    0      │
   30      ├─ SET lock tokA NX PX 800 ✓
    │      │  拿到锁，开始干活
  100      │                              ├─ SET lock tokB NX PX 3000 ✗
    │      │                              │  （A 还持着）
  830      │  ┌───────────────────────────┴─────────────────────────────┐
    │      │  │ A 的锁在这里静默过期了 —— A 自己不知道                    │
    │      │  └───────────────────────────────────────────────────────┘
  900      │                              ├─ SET lock tokB NX PX 3000 ✓
    │      │                              │  拿到锁！B 进临界区
 1500      ├─ DEL lock  ← 删的是 tokB！
    │      │  （A 以为自己收工了）          │  B 还以为自己持有
 1600      │                              │                     ├─ SET lock tokC NX PX 3000 ✓
    │      │                              │                     │  拿到锁！
    │      │                              │                     │
    │      ▼                              ▼                     ▼
    │   ┌────────────────────────────────────────────────────────────┐
    │   │  B 和 C 同时在临界区 —— 互斥被破坏，而两边都「加了锁」       │
    │   └────────────────────────────────────────────────────────────┘
 2000      │                              ├─ GET lock → "tokC"
    │      │                              │  「已经被别人拿走了，但我不知道」
```

**修法**：释放时用 Lua 把「比较 value」和「删除」做成一个原子操作：

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end
```

### 二、实测（Redis 7.4.11 + PHP 8.4.25）

脚本：`../bench/redis/q30-lock.php`（`docker exec learn-php php /app/bench/redis/q30-lock.php <lost-update|no-expire|wrong-del|lua-del|watchdog|reentrant>`）

多进程用**绝对时刻调度** `at($base, $offsetMs)` 对齐，而不是 `sleep` 相对时间——进程启动、自动加载的耗时会漂，相对写法跑出来的时序每次都不一样。

**1. 为什么需要锁**（20 进程 × 100 次 `GET` → `usleep(1ms)` → `SET`）

| 做法 | 期望 | 实际 | 丢 | 耗时 |
| --- | ---: | ---: | ---: | ---: |
| 无锁 | 2,000 | **109** | 1,891（**94.5%**） | 1.56 s |
| `SET NX PX` | 2,000 | **2,000** | 0（**0.0%**） | 8.13 s |

代价很清楚：**锁把 1.56 s 拉长到 8.13 s（5.2 倍）**，因为临界区被串行化了。

**2. `SETNX` + `EXPIRE` 分开写会怎样**

```
1) 客户端 A: SETNX q30:lock:noexp tokA → true
   A 本来打算下一步 EXPIRE 30，但在这一步之前进程被 kill / 网络断了
   现在这个 key 的 pttl = -1  (-1 = 永不过期)

2) 客户端 B 尝试加锁 20 次，每次间隔 100ms：
   成功 0 / 20 次，key 的 pttl 依然是 -1 —— 这把锁永远不会自己开
```

对比：合成一条 `SET NX PX 1500` 后，写入时 `pttl=1500`，1.6 秒后 `pttl=-2`（**已自动释放，别人现在能拿到**）。

**3/4. 误删 vs Lua 校验**（同一时序，只改释放方式）

| | 直接 `DEL`（wrong-del） | Lua 校验（lua-del） |
| --- | --- | --- |
| A t=1500ms 释放 | **DEL 执行了** | **发现自己已经不是持有者，什么都没删** |
| C t=1600ms 加锁 | **成功**（此刻 B 还以为自己持有） | **失败**（锁还在 B 手里，互斥成立） |
| B t=2000ms 自查 | 发现锁是 `tokC`，**已被别人拿走** | 锁还是 `tokB`，**确实还是我** |
| 结论 | **A 在 1500ms 删掉的是 B 的锁，C 随即拿到锁。B 和 C 同时认为自己在临界区** | **互斥从头到尾成立** |

**5. 看门狗续期**（锁 `TTL=800ms`，但持锁者要干 4,200 ms）

| | A（持锁者） | B（等待者） | 互斥 |
| --- | --- | --- | --- |
| **不续期** | 在 **t=814ms** 发现锁已经不在自己手里 | t=**822ms** 抢到（早于 A 释放 4228ms） | **破坏** |
| **看门狗自动续期** | 全程持有，4,200 ms 内一刻都没丢 | t=**4222ms** 才抢到（晚于 A 释放 4213ms） | **成立** |

**6. 可重入锁**（hash 存「持有者 → 重入次数」）

```
A 加锁 1 次 : 1   hgetall={"tokA":"1"}
A 再加 1 次 : 1   hgetall={"tokA":"2"}      ← 同一个 token 可以重复进入
B 加锁      : 0   hgetall={"tokA":"2"}      ← 0 = 被挡住
A 释放 1 次 : 1   hgetall={"tokA":"1"}      ← 还在，计数减到 1
B 加锁      : 0   hgetall={"tokA":"1"}      ← 依然 0，A 的计数没归零
B 直接释放  : 0   hgetall={"tokA":"1"}      ← 0 = 不是自己的锁，删不掉
A 释放 2 次 : 1   hgetall={}                ← 计数归零，锁被删
B 加锁      : 1   hgetall={"tokB":"1"}      ← 现在才轮到 B
```

### 三、四个反直觉的点

**1. `SETNX` + `EXPIRE` 不是「稍微不安全」，是「错得很严重」。** 实测 B 连续尝试 20 次全部失败、锁 `pttl=-1` 永不过期——**一个进程在两步之间崩溃，这把锁就永久泄漏**，整个业务线卡死。必须用 `SET key val NX PX ms` 一条命令（Redis 2.6.12+ 支持），它把「不存在才设置」和「设置过期」做成了原子操作。

**2. 「锁过期」比「锁泄漏」更隐蔽也更危险。** 泄漏了你立刻能发现（业务卡住）；过期了什么都看不出来——A 还以为自己持有锁、B 也以为自己持有锁，**两边都在写数据，而且日志里一切正常**。实测不续期时 A 在 814 ms 就失去了锁，但它直到 4228 ms 才「收工释放」——**中间 3.4 秒它一直在裸奔**。**TTL 必须大于业务耗时的 p99.9**，拿不准就上自动续期。

**3. 看门狗续期本身也要用 Lua 校验持有者。** 否则会续到别人的锁上——A 的锁过期、B 拿到，A 的看门狗把 **B 的锁**又续了 30 秒。本文的实现是 `if get(KEYS[1])==ARGV[1] then pexpire(...) else return 0 end`。另一个细节：续期间隔要**小于 TTL 的 1/3**，本文 TTL=800 ms、每 50 ms 续一次（保守值）。

**4. 加锁的代价是 5.2 倍延迟（1.56 s → 8.13 s）。** 锁把并发变成串行，这是它的本质不是缺陷。**能用「无锁的原子操作」解决的（`INCR`、`SET`、`HSET`）就别用锁**——本文那个「读-改-写」计数器的正确解法是 `INCR`，一次原子操作，既没有丢失也没有串行化。

### 四、实战结论

| 场景 | 结论 |
| --- | --- |
| 加锁 | `SET key token NX PX <ttl>`。**`token` 必须是每个请求唯一的随机值**（本文用 `bin2hex(random_bytes(8))`），否则 Lua 校验没有比较基准 |
| 解锁 | **必须用 Lua 比较 value 再删**。直接 `DEL` 实测会删掉别人的锁，导致两个进程同时在临界区 |
| 续期 | 有长任务就上自动续期，**续期脚本也要校验 value**。间隔 ≤ TTL/3 |
| TTL 定多少 | 大于业务耗时 p99.9，同时小于「业务不可用能容忍的时长」。两者冲突说明**临界区设计有问题**，该拆 |
| 拿不到锁怎么办 | 必须设**总超时**（自旋 N 次或 M 毫秒后放弃），否则会无限等待。本文的 `lost-update` 场景用的是自旋 200 µs 一次、无上限（只适合测试） |
| 能不用锁就别用 | 计数器用 `INCR`、去重用 `SET NX`、状态机用 Lua 脚本原子执行。**锁是最后手段** |
| 可重入 | 用 hash：`HINCRBY key token 1` 加锁、`HINCRBY key token -1` 解锁、归零时 `DEL`。非重入场景不要用（复杂且更慢） |
| 单点问题 | 单实例 Redis 挂了，所有锁失效。**Redlock（多实例多数派）本环境未实测**，且它本身有争议（依赖时钟假设）。要有更强保证用 etcd/ZooKeeper |
| 主从切换 | 主库加锁成功但还没同步就宕机，从库升主后锁消失，另一个客户端能拿到同一把锁。**本环境无主从，未实测** |
| 上线前必做 | 至少验证三件事：**释放是否校验 value**、**TTL 是否大于 p99.9**、**拿不到锁是否有超时** |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| `SET NX PX` 是原子的吗？ | 是。Redis 的命令执行是单线程的，一条 `SET` 命令里的「判存在 + 设置 + 设过期」在一个命令内完成，中间不会插入其他客户端的命令。`SETNX` + `EXPIRE` 是两条命令，中间可以插入任何东西（包括你的进程崩溃） |
| 为什么解锁要用 Lua 而不是 `WATCH`/`MULTI`？ | `WATCH` + `MULTI` 需要额外往返（`WATCH` 一次、`MULTI`/`EXEC` 一次），且失败要重试。Lua 一次往返、服务端原子执行，**更快也更简单**。Redis 7 也可以考虑 `FUNCTION` |
| Lua 脚本能保证原子性吗？ | 能，但有前提：脚本执行期间**不会被打断**（Redis 单线程），所以整个脚本是一个原子块。风险是**慢脚本会阻塞所有人**（见 Q25），别在锁脚本里写循环 |
| 锁的 value 用 UUID 还是别的？ | 只要**能区分不同持有者**就行。实践上 UUID/`random_bytes` 最常见。不要用 `getmypid()`——不同机器会撞 |
| 看门狗的间隔怎么定？ | 经验值是 TTL 的 1/3（留两次重试机会）。本文 TTL=800 ms 用 50 ms，偏保守。间隔太密会浪费往返，太疏则单次续期失败就丢锁 |
| Redlock 到底行不行？ | 争议点是「依赖各实例时钟不发生大漂移」。Kleppmann 的批评是「时钟跳变会导致两人同时持锁」，Antirez 的回应是「需要人为调整时钟才会触发」。**本文未实测，不站队**——工程上更稳的做法是用有租约（lease）语义的 etcd/ZooKeeper |
| 有没有更简单的方案？ | 如果临界区是「一个数据库事务」，直接用数据库的行锁/唯一索引更可靠；如果是「幂等操作」，用唯一键去重比锁更简单。**锁适合「跨资源、非幂等」的临界区** |
| 锁被删了业务还在跑怎么办？ | 无解——这是分布式锁的固有风险（fencing token 问题）。标准解法是给每次持锁分配一个**单调递增的 fencing token**，下游资源（如数据库）校验 token 只接受更大的，从而拒绝过期持有者的写入。**本环境未实测** |

## Q31. 热 Key 与大 Key

### 结论

大 Key 的危害**不在「元素多」，在「内部节点多」**。实测同样 500,000 个元素、同样一个 `DEL`（服务端耗时取自 `SLOWLOG`）：

| 类型 | 编码 | 内存占用 | 服务端耗时 | µs/元素 |
| --- | --- | ---: | ---: | ---: |
| list | quicklist | 4,422,928 B | **90 µs** | 0.00018 |
| hash | hashtable | 30,594,416 B | **157,483 µs** | 0.315 |
| set | hashtable | 23,394,416 B | **49,615 µs** | 0.099 |
| zset | skiplist | 46,315,304 B | **61,565 µs** | 0.123 |

**hash 的删除耗时是 list 的 1,750 倍**，尽管内存只差 6.9 倍。原因是 quicklist 把元素打包进 listpack，一次 `zfree` 释放一大片（每个节点约 700 个元素）；而 hashtable / skiplist 每个元素一个节点，只能逐个释放。

**130+ 毫秒意味着什么**：另一个客户端在这段时间里的最坏一次 `PING` 往返是 **133.77 ms**，而且**正好落在 `DEL` 发起的那一档**（操作前 680 ms 内的基线一直在 0.14~0.64 ms）——**整个 Redis 实例被一条 `DEL` 冻结**。换成 `UNLINK`，命令自身只花 **0.26 ms**，旁人的最坏 `PING` 是 **0.88 ms**（而且出现在最开头那一档，是探针自己的启动抖动，不是操作造成的）。

热 Key 的发现：`--hotkeys` 需要 LFU 淘汰策略，而 `OBJECT FREQ` 读出来的**不是访问次数**——同一个 key 读 200 次，`lfu-log-factor=10` 时 `freq=12`、`=1` 时 `freq=27`；而**从没读过的 key 也是 5**（`LFU_INIT_VAL`）。

### 一、大 Key 的代价在哪

```
  同样是 500,000 个元素，内部结构完全不同：

  list（quicklist）
  ┌────────┐ ┌────────┐ ┌────────┐        ┌────────┐
  │listpack│ │listpack│ │listpack│  ...   │listpack│   每个 listpack 约 700 个元素
  │ ~8 KB  │ │ ~8 KB  │ │ ~8 KB  │        │ ~8 KB  │   → 约 715 个节点
  └────────┘ └────────┘ └────────┘        └────────┘
   DEL 需要 zfree 的次数：~715            实测 90 µs

  hash（hashtable）
  ┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐
  │dict││dict││dict││dict││dict││dict│ ...       每个字段一个 dictEntry
  │Ent ││Ent ││Ent ││Ent ││Ent ││Ent │           + key sds + value sds
  └────┘└────┘└────┘└────┘└────┘└────┘
   DEL 需要 zfree 的次数：~1,500,000      实测 157,483 µs

   ┌───────────────────────────────────────────────────────────┐
   │ 元素数一样，释放次数差约 2000 倍 → 阻塞时间差 1750 倍        │
   └───────────────────────────────────────────────────────────┘
```

**阻塞被别人感知到的样子**（`DEL` 一个 500k 字段的 hash，探针每 20 ms 记最坏 PING）：

```
  每 20ms 最坏 PING 往返(ms)          DEL              UNLINK

### 三、四个反直觉的点

**1. 「大 Key」的危害取决于「内部节点数」，不是「元素数」。** 实测：500k 元素的 list（4.4 MB）删除只要 **90 µs**；500k 字段的 hash（30.6 MB）要 **157 ms**——内存差 6.9 倍，耗时差 **1,750 倍**。所以「元素超过 5000 就是大 Key」这种按个数定的规则是错的；**要按内存和结构类型定**。真正的判据是「这个 key 的操作会不会阻塞主线程」。

**2. 用 `date +%s%N` 包住 `redis-cli DEL` 来量耗时，量到的是 `redis-cli` 自己的启动开销。** 本文第一版就是这么翻车的：1M 元素的 list 量出 `DEL 5 ms`、`UNLINK 5 ms`——两个数一样，因为 4~5 ms 全是 `fork`+`exec`+连接。**必须用持久连接，或者读 `SLOWLOG`**。改完之后才看到 157 ms 和 30 µs 的真实差距。

**3. `OBJECT FREQ` 不是「访问次数」，是概率性的对数计数器。** 读 200 次的 key，`lfu-log-factor=10` 读到 12，`=1` 读到 27——**差一倍多**。而且同一个配置多跑几次，结果还会小幅抖动（因为计数越高越难再加一，递增是概率性的）。更反直觉的是：**从没读过的 key `freq=5` 而不是 0**，因为新 key 一律以 `LFU_INIT_VAL`(5) 起步，免得刚写进来还没被读就被淘汰。所以 `--hotkeys` 输出里一堆 `counter: 5`，得自己看分布判断谁是真热。

**4. `UNLINK` 不是「免费」，是「把一次大停顿换成很多小停顿」——而且小停顿的量级取决于你对比谁。** 实测 `UNLINK` 的命令自身只花 **0.26 ms**（释放交给 bio 线程），旁人的最坏 `PING` 是 **0.88 ms**。0.88 ms 相对 `DEL` 的 133.77 ms 当然微不足道，但**它相对 `DEL` 之前那 680 ms 里 0.14~0.64 ms 的基线，仍然是可见的抬升**（基线里最大 0.64 ms，UNLINK 轮里出现了 0.88 / 0.78 / 0.57）。后台线程释放会和主线程抢分配器，代价是摊开的、不消失的。

### 四、实战结论

| 场景 | 结论 |
| --- | --- |
| 大 Key 的判据 | **按内存和操作阻塞时间来定，不按元素个数**。经验线：string > 10 KB、集合类 > 5,000 元素**或** > 1 MB 就要警惕。真正的标准是「删除/读取它会不会造成可感知的停顿」 |
| 发现大 Key | `redis-cli --bigkeys`（按类型扫最大的 key，可线上跑）；`--memkeys`（按内存排序，需要 Redis 6+）；精确值用 `MEMORY USAGE key SAMPLES 0` |
| 注意 `--bigkeys` 的误导 | 它按**元素个数**排序。实测 `q31:list500k`（50 万元素、4.4 MB）会排在 `q31:hash300k`（30 万字段、21.5 MB）前面——**元素多不等于内存大** |
| 删大 Key | **一律用 `UNLINK`**。实测 `DEL` 阻塞 133~185 ms，`UNLINK` 只花 0.18~0.26 ms |
| 集群环境删大 Key | 单实例 `UNLINK` 就够了。Redis 4.0+ 可以用 `redis-cli --cluster` 配合 `UNLINK` 批量处理。**Cluster 环境本环境未实测** |
| 拆大 Key | hash 按业务主键分片（每片 100~200 字段，见 Q26 的 512 悬崖）；list/zset 按时间或 ID 区间分片。**分片同时解决内存和阻塞两个问题** |
| 热 Key 发现 | 需要 `maxmemory-policy` 为 `allkeys-lfu` 或 `volatile-lfu`，然后 `redis-cli --hotkeys`。**注意它会扫全库**，大实例上要评估开销 |
| 热 Key 处理 | 本地缓存（APCu / Swoole Table）；或复制成 N 份加随机后缀分散读；或读写分离加从库。**这些本环境都未实测** |
| 大 value 的传输 | 实测 1 MB 的 `GET` 往返 **436.0 MB/s**（单次 2.2935 ms）。**1000 QPS 命中这个 key ≈ 0.9 GB/s 出口带宽**——网卡会先于 Redis 崩。压缩能缓解，但吃 CPU |
| 监控 | 定期 `--bigkeys` 报告 + 单 key 的 `MEMORY USAGE` 基线。突变要告警 |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| 为什么 quicklist 这么快？ | 它是「listpack 的双向链表」：每个节点是一个 8 KB 的 listpack，装约 700 个元素。释放时按节点释放，所以是 O(节点数) 而不是 O(元素数)。代价是 `LINDEX` 要按节点跳，但比纯链表的 O(N) 好得多 |
| 那 list 是不是可以随便用？ | 不是。它仍然是**单个 key**——Cluster 里整个 key 落在一个分片上，几十 GB 的 list 会把那个分片打爆；而且 `LRANGE k 0 -1` 依然会阻塞。**`DEL` 便宜不代表其他操作便宜** |
| `UNLINK` 之后内存马上释放吗？ | 不是，是异步的。用 `INFO memory` 的 `lazyfree_pending_objects` 看队列深度（实测 `UNLINK` 后立刻是 `1`，后台线程干完回 `0`）。也有 `lazyfree-lazy-expire`、`lazyfree-lazy-eviction` 等开关让过期/淘汰也走异步 |
| 大 Key 怎么拆？ | hash：`HGET key:{id % N}`，N 取 100 左右；list：按时间分（`list:20260920`）；zset：按分数区间分。**关键是让客户端知道怎么定位分片**，通常把分片号编进 key |
| `MEMORY USAGE` 准吗？ | 默认采样会估歪，`SAMPLES 0` 是全量走一遍。实测同一个 300k 成员的 zset：**默认采样连跑 3 次都是 28,852,256**（一模一样，因为它总是取开头几个元素外推，误差是**系统性偏差**不是随机抖动），而 `SAMPLES 0` 连建 4 次是 31,242,464 ~ 31,251,176（差 0.028%，≈104.2 B/成员）——**采样版稳定偏低 7.7%**。注意 `SAMPLES 0` 对大 key 本身有开销 |
| 热 Key 一定要 LFU 吗？ | `--hotkeys` 需要。没有 LFU 时可以靠 `MONITOR`（生产禁用，开销极大）或客户端埋点统计。**`OBJECT FREQ` 只在 LFU 策略下可用**，换成 `noeviction` 会报错 |
| LFU 计数器会衰减吗？ | 会。`lfu-decay-time` 默认 60（分钟），按「上次访问距今过了几个 60 分钟」减计数。所以**长期看，一个 key 的热度是「最近的热度」而不是「累计热度」** |
| 热 Key 用本地缓存一致性问题怎么办？ | 本地缓存无法被 Redis 的 `DEL` 感知，只能靠短 TTL（秒级）或广播失效（Redis Pub/Sub 通知所有节点）。**本环境未实测**——属于架构取舍 |
| Cluster 下热 Key 怎么办？ | 没法把单个 key 拆到多个分片（同一个 key 必然落一个 slot）。要靠「读写分离 + 多个只读副本」或「本地缓存 + 逻辑过期」扛。**本环境无 Cluster，未实测** |
