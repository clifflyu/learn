## Q46. 设计一个高并发秒杀系统，如何防超卖和防刷？

### 结论

**超卖的根因不是「没加锁」，而是「判断」和「扣减」是两个动作。** 只要这两步之间有窗口，
并发就能穿过去，而且**并发数不超过库存数时它看起来完全正确** —— 这就是这类 bug 能上线的全部原因。

实测（100 并发抢 100 件）里最刺眼的一组数字：**同一段「先 SELECT 判空再扣减」的代码，
100 并发时卖出 100 件、超卖 0、一切正常；把并发提到 200，立刻卖出 200 件、库存被打到 -100、超卖 100 件。**

正确姿势只需一句话：**把「判断」和「扣减」压成一条原子语句** —— 要么 `UPDATE ... WHERE stock > 0` 看影响行数，
要么 `SELECT ... FOR UPDATE` 放进事务，要么 Redis Lua。三种都能做到超卖恒为 0，差别只在吞吐。

防刷则在**请求到达库存判断之前**就要拦掉，两道闸：Redis 频控（单用户 N 秒一次）+ 数据库唯一键（一人一单兜底）。

### 一、秒杀链路的四道闸

库存判断放在哪一层，决定了系统能扛多少 QPS。越靠前越便宜：

```
   浏览器 / 客户端
        │
        │  ① 静态资源与秒杀页：全部 CDN，请求根本到不了后端
        ▼
┌───────────────────────────────────────────────────────────────────┐
│② 接入层（Nginx / 网关）                                           │
│   · 单 IP / 单用户 QPS 限流   · 答题、验证码、签名校验            │
│   · 目的：把瞬时百万请求砍到万级，再过不去的直接返回              │
│   实测：非原子「GET 判断 + SET」写法 50 并发漏过 11 个            │
│         换成 SET NX EX 后稳定放行 1 个（见下文实测 A / B）        │
└───────────────────────────────────────────────────────────────────┘
        │  剩下 1 万 QPS
        ▼
┌───────────────────────────────────────────────────────────────────┐
│③ 应用层：Redis 原子预扣（Lua：判空 + 扣减 + 入队，一个原子操作）  │
│   · 库存判断只发生在 Redis，请求路径完全不碰 MySQL                │
│   · 实测 134~863 QPS（3 轮），比 MySQL 乐观锁高一个数量级         │
└───────────────────────────────────────────────────────────────────┘
        │  lPush，只有抢到的才入队
        ▼
┌───────────────────────────────────────────────────────────────────┐
│④ 队列（Redis List / MQ）：把 1 万 QPS 的尖峰削成 500 的平稳流     │
└───────────────────────────────────────────────────────────────────┘
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│⑤ 消费者批量落库：MySQL 是最后一道库存约束，不是第一道             │
│   UPDATE stock SET stock=stock-1 WHERE goods_id=? AND stock>0     │
│   或 INSERT INTO orders ... SELECT ... WHERE stock > 0（一条语句）│
└───────────────────────────────────────────────────────────────────┘
```

**关键判断：库存判断放 Redis 还是 MySQL？**
Redis 快，但 Redis 的库存是「预扣」，和 DB 会有短暂不一致（进程崩了要补偿）。
所以生产上是 **Redis 挡流量 + MySQL 兜底约束**，两道都要有 —— Redis 挂了不能让库存变负，MySQL 慢了不能拖垮前端。

### 二、实测（MySQL 8.4.11 / Redis 7.4.11 / PHP 8.4.25）

脚本 `../bench/design/02-seckill.php`。方法：每个并发请求 = 一个 `pcntl_fork` 出来的独立进程 + 独立 PDO/Redis 连接，
贴近「PHP-FPM 多 worker 各跑各的」的真实形态；用 socket 闸门让所有进程在**同一毫秒**发车（派发抖动见下表，都在百毫秒内）。

**事实来源是 `orders` 表的行数**，不是 `stock` 字段 —— 库存字段算错了，订单条数不会骗人。

> 方案 7 的库存在 Redis 里预扣，DB 的 `stock` 字段**不参与秒杀**，所以它读出来还是 100 ——
> 这正是「账实差 100」的来源。**这里不是算错了，而是库存的权威副本在这一刻是 Redis，不是 MySQL**；
> 消费者落库时才会同步过去。**如果把这个账实差当成 bug 去「修」，就会把预扣模式改回同步扣减，秒杀也就白设计了。**
> 方案 6 的 QPS 三轮是 134 / 183 / 863，波动全部来自共享 Redis 的邻居负载（见下文 C 节的噪声说明）。

**这份表里最危险的一行是第一行：超卖 0、账实差 0、100 个请求全部成功、一切看起来完美。**
方案 2 的「账实差 94」是唯一露馅的地方：订单卖出 100 件、库存实际剩 0，但 `stock` 字段还写着 94 ——
**94 件幽灵库存**，下一次活动会把这 94 件再卖一遍。

| 2 无防护B：PHP 算好新值写回 | **200** | **0** | **200** | 93~98 | **+100** | 193~198 | 0.68~1.59 | 686~1373 | 126~293 | 100 |
| 3 悲观锁 `SELECT ... FOR UPDATE` | 100 | 100 | 100 | 0 | **0** | 0 | 2.92~3.83 | 2913~3800 | 26~34 | 100 |
| 4 乐观锁 `UPDATE ... WHERE stock > 0` | 100 | 100 | 100 | 0 | **0** | 0 | 1.26~1.66 | 1272~1672 | 60~79 | 100 |
| 5 Redis `DECR` 判定 | 100 | 100 | — | — | — | — | 0.41~0.63 | 258~458 | 158~246 | **-100** |
| 6 Redis `Lua` 判空+扣减 | 100 | 100 | — | — | — | — | 0.60~0.72 | 509~642 | 139~166 | **0** |

**超卖 100 件，三轮复现 3/3，库存字段被打成 -100。** 这就是这题最有说服力的证据。

同一份代码，只是并发从 100 提到 200，从「完全正确」变成「超卖一倍库存」——
**如果你的压测并发没超过库存数，你测了个寂寞。**

方案 5 的 `Redis 剩余 = -100` 是另一个坑：`DECR` 的返回值确实一人一个、不会超卖，
但 key 被扣到 -100 之后，你**没法区分「卖完了」和「超卖了 100 件」**，也没法从 key 本身恢复出真实销量。
方案 6 的 Lua 在脚本里先判空再扣，key 精确停在 0。

#### 悲观锁 vs 乐观锁

两者超卖都是 0，差距全在吞吐。200 并发下的总耗时（三轮均值）：

| 方案 | 200 并发耗时(s) | 相对倍数 | p99(ms) | QPS |
| --- | ---: | ---: | ---: | ---: |
| 悲观锁 `SELECT ... FOR UPDATE` | **3.39** | 1.00（基准） | 2913~3800 | 26~34 |
| 乐观锁 `UPDATE ... WHERE stock > 0` | **1.45** | **0.43（快 2.3 倍）** | 1272~1672 | 60~79 |

差距的来源是**行锁持有时间**：悲观锁在「SELECT ... FOR UPDATE」到「COMMIT」之间一直占着这行，
中间还夹着一条 INSERT 语句的网络往返；乐观锁只有一条 UPDATE，加锁到释放之间没有别的往返。
库存行是**热点中的热点**，锁持有时间直接决定排队长度 —— 差 2.3 倍很正常。

#### 防刷实测（脚本 `../bench/design/03-antibrush.php`，同一用户 50 并发）

| 方案 | 放行 | 拦截 | 结论 |
| --- | ---: | ---: | --- |
| A 非原子 `EXISTS` 判断 + `SET` | **11** | 39 | 错误写法。窗口内本该只放行 1 个，实测漏过 **11** 个 |
| B `SET NX EX`（判断+占位+过期一条命令） | **1** | 49 | 正确。50 个不同用户各发 1 次 → 放行 50 / 拦截 0，不误伤 |
| C `INCR` + 单独 `EXPIRE` | 5 | 45 | 计数对，但 TTL 不原子（坑见下） |
| D Lua 原子 `INCR` + `EXPIRE` | 5 | 45 | 正确。计数和 TTL 一定同时存在 |
| E1 固定窗口 2s 分桶，限额 5 | **10** | **0** | 两批各 5 个、相隔 0.2s 跨窗口边界 → 限额形同虚设 |
| E2 滑动窗口（ZSet），同样时刻发车 | 5 | 5 | 批 1 的 5 条记录仍在 2s 窗口内，第二批一个都过不去 |
| F 一人一单：`orders.uk_goods_user` 唯一键 | 1 | 49 | 最后一道防线，50 并发只落 1 行 |

**C 的坑要单独说**：`INCR` 的原子性没问题，`EXPIRE` 单独发也没问题，问题是**两条命令之间可能死人**。
实测模拟「INCR 之后、EXPIRE 之前进程被 kill」：计数 = 7，**TTL = -1（永不过期）**——
这个用户被**永久限流**，而且从监控上完全看不出来（计数看着很正常）。

### 三、五个反直觉的点

**1. 并发数不超过库存数时，「先查后改」是完全正确的。**
实测 100 并发抢 100 件：方案 1 卖出 100 件、超卖 0、失败 0，**每一项指标都正常**。
因为 100 个请求的 `SELECT` 都发生在 `UPDATE` 落库之前，「判空」那道 if 一次都没生效 ——
但它也一次都不需要生效，因为库存正好够。**这类 bug 的特征就是「上线半年都没事，第一次真秒杀就炸」。**

**2. 超卖 0 不等于库存对。** 方案 2 在 100 并发下超卖也是 0，但 `stock` 字段剩 94、实际剩 0，
凭空多出 94 件**幽灵库存**。所以核对库存要用两个指标：
`超卖 = 订单数 - 库存总量`，`账实差 = 最终库存 - (库存总量 - 订单数)`。
只看超卖会漏掉「丢失更新」，只看库存字段会漏掉「超卖」。

**3. 乐观锁比悲观锁快 2.3 倍，而且并发越高差距越大。**
直觉上「锁」是慢的、「事务」是重的，应该悲观锁更慢 —— 这个方向对，但量级容易估错。
实测 200 并发：悲观锁 3.39 s、乐观锁 1.45 s。原因是热点行的锁持有时间：
悲观锁要跨「SELECT FOR UPDATE → UPDATE → INSERT → COMMIT」四次网络往返，
乐观锁只有一次 UPDATE。**热点行上，少一次往返就是少一截排队。**

**4. `DECR` 不超卖，但会把 key 扣成负数，这比超卖更难排查。**
实测 200 并发抢 100 件：`DECR` 方案刚好 100 个请求拿到 `>= 0` 的返回值，超卖没有发生，
但 key 最终是 **-100**。业务上你拿不到「真实卖出多少」这个数 —— 恢复库存时只能靠日志重放。
Lua 版同样是 100 成功 / 100 失败，但 key 精确停在 **0**。**「不超卖」和「库存数可恢复」是两件事。**

**5. 固定窗口的突刺不是理论问题，是必然发生的。**
限额 5 次 / 2 秒，两批各 5 个请求、相隔 0.2 秒、正好跨窗口边界 → 实测放行 **10 个、拦截 0 个**，
限额翻倍。同一时刻发车换滑动窗口（ZSet）→ 放行 5 / 拦截 5。
真实用户完全不需要卡点：只要在窗口末尾点几下、窗口开头再点几下，就能把限额翻倍。

### 四、实战结论

| 场景 | 选择 | 实测依据 |
| --- | --- | --- |
| 单机、并发不高（< 500 QPS） | `UPDATE ... WHERE stock > 0` + 影响行数 | 超卖 0，比悲观锁快 2.3 倍，代码最短 |
| 需要「查出库存再判断」的复杂逻辑 | `SELECT ... FOR UPDATE` 放事务里 | 超卖 0，但热点行吞吐只有乐观锁的 43% |
| 高并发秒杀（万级 QPS） | Redis Lua 预扣 + 异步入队 | 863 QPS，请求路径不碰 MySQL |
| 分布式、多实例扣减 | Redis Lua（`DECR` 单独用会扣成负数，不可取） | Lua 版 key 停在 0，`DECR` 版停在 -100 |
| 单用户频控 | `SET key 1 NX EX N` | 50 并发放行 1 个，不同用户不误伤 |
| 接口限流（N 次 / 窗口） | Lua 原子 `INCR`+`EXPIRE`，**窗口用滑动** | 固定窗口实测被跨边界翻倍 |
| 防刷最后一道防线 | DB 唯一键 `uk_goods_user` | 50 并发只落 1 行 |
| 库存核对 | `超卖` 和 `账实差` 两个指标一起看 | 只看超卖漏掉丢失更新，只看库存漏掉超卖 |
| 压测并发数 | **必须 > 库存数** | 100 并发抢 100 件，超卖 0；200 并发，超卖 100 |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| `SELECT ... FOR UPDATE` 没走索引会怎样？ | 锁住全表（间隙锁），吞吐直接崩。必须走主键或唯一索引 |
| 乐观锁 `UPDATE` 返回 0 怎么区分「卖完了」和「行不存在」？ | 返回 0 一律当失败处理即可；要区分就再查一次，但别在事务里查 |
| Redis 预扣成功了，消费者落库失败怎么办？ | 队列必须可靠（Redis List 用 BRPOPLPUSH 备一份 processing 队列）+ 定时对账补偿 |
| Redis 主从切换丢预扣怎么办？ | 秒杀库存用 Redis 但接受少量丢失，靠 MySQL 的 `WHERE stock > 0` 兜住最终不超卖 |
| `DECR` 和 Lua 差在哪？ | `DECR` 无脑减，`Lua` 先判空。少一次判断，key 就从 -100 变成 0 |
| 限流 key 用 `INCR` 但 TTL 忘了设？ | 用户被永久限流且监控无异常。必须用 Lua 把 `INCR`+`EXPIRE` 绑成一个原子操作 |
| `SET NX EX` 和 `SETNX` + `EXPIRE` 差在哪？ | 后者两个往返，中间进程死掉就是一把永不过期的锁 |
| 固定窗口和滑动窗口怎么选？ | 精度要求高用滑动（ZSet）；只做粗略保护用固定窗口，但要接受边界翻倍 |
| 一人一单用 Redis Set 还是 DB 唯一键？ | 都要。Redis 拦绝大多数，DB 唯一键是最后防线（实测 50 并发只落 1 行） |
| 秒杀为什么要答题 / 验证码？ | 把机器请求挡在库存判断之前。它保护的不是库存逻辑，是整条链路的 QPS |

## Q47. 设计订单超时自动关闭，有哪几种方案？如何保证不重复关闭？

### 结论

三种方案的差别在**「谁来发现这张订单到期了」**：

| 方案 | 谁发现 | 精度 | 代价 |
| --- | --- | --- | --- |
| 定时轮询扫表 | 自己轮询 | **= 轮询间隔**（平均延迟 ≈ 间隔 / 2） | 每秒固定扫表，间隔越短扫得越勤 |
| Redis 过期键 + 监听 | Redis 主动推 | 受 Redis 过期策略影响（**惰性 + 定期采样，不保证准点**） | pub/sub 不持久，重启期间的到期通知全丢 |
| 延迟队列（ZSet） | worker 轮询 ZSet | = 轮询间隔，但**只捞「到点的那几个」** | 需要额外维护一个 ZSet 和 worker |

**实测精度**：轮询 1000 ms → 关闭延迟 525 ms；轮询 100 ms → 延迟 30 ms；Redis 通知 → 中位 148 ms；
ZSet 队列 → 最小延迟 **9~18 ms**（等于标定的空轮询间隔 10.5~11.0 ms）。

**不重复关闭靠两样东西，实测数据非常干脆：**
- **状态机**：`UPDATE ... WHERE id = ? AND status = 0`，看影响行数 —— 4 个 worker 抢 100 张订单，
  **生效关闭 100 次、被幂等拦下 300 次、重复关闭 0 张**；
- **唯一约束**：`close_log.uk_order`，重复的 INSERT 直接吃 1062 —— 同样 100 / 300 / 0。

不加任何防护的版本：**400 次关闭动作、100 张订单全部被重复关闭、单张最多关 4 次。**

### 一、三种方案的链路

```
【A】定时轮询扫表
  ┌──────────┐  每 N 秒      ┌─────────────────────────────────────┐
  │  crontab │ ────────────► │ SELECT id FROM orders               │
  │  或常驻  │               │ WHERE status=0 AND expire_at<=NOW() │
  │  worker  │               │ ORDER BY expire_at LIMIT 500        │
  └──────────┘               └─────────────────────────────────────┘
                                        │ 走 idx_status_expire
                                        ▼
                              UPDATE orders SET status=2 ... WHERE id IN (...)
  精度 = 轮询间隔。平均延迟 ≈ 间隔 / 2（到期时刻在间隔内均匀分布）
  ✔ 实现最简单、不依赖外部组件、漏掉的下一轮一定补上
  ✘ 间隔短则空轮询多，间隔长则延迟大；多实例要抢锁

【B】Redis 过期键 + keyspace notification
  ┌──────────┐  SET order:expire:{id} EX 1800  ┌─────────┐
  │  下单     │ ─────────────────────────────► │  Redis  │
  └──────────┘                                 └────┬────┘
                                                   │ 到期时主动发事件
                        ┌──────────────────────────▼──────────────────┐
                        │ 订阅 __keyevent@0__:expired                 │
                        │ （需要 notify-keyspace-events 含 E 和 x）   │
                        └──────────────────────────┬──────────────────┘
                                                   ▼
                                          关闭订单 + 幂等守卫
  ✔ 不用轮询，事件驱动，服务端主动推
  ✘ pub/sub 不持久：订阅者掉线 / 重启期间的通知**永久丢失**（要靠对账兜底）
  ✘ 过期**不保证准点**：Redis 是「惰性删除 + 定期采样删除」，
     key 到点了但没人访问、采样又没扫到，事件就会晚发甚至等到下次访问才发

【C】延迟队列（Redis ZSet）
  下单 ──► ZADD q47:delay <到期毫秒时间戳> <order_id>
                                              │
                        ┌─────────────────────▼─────────────────────┐
                        │worker 循环：                              │
                        │  ZRANGEBYSCORE q47:delay -inf <now_ms>    │
                        │                LIMIT 0 100                │
                        │  ↓ 拿到「已经到点」的订单                 │
                        │  ZREM q47:delay <id>   ← 返回值即抢占结果 │
                        │  ↓ 抢到的才处理                           │
                        │  关闭订单（状态机 / 唯一约束兜底）        │
                        └─────────────────────┬─────────────────────┘
  ✔ 只捞到点的那几个，空轮询代价极低；精度 = 轮询间隔；天然支持多 worker
  ✘ 要自己维护 ZSet 的一致性和积压监控；重启后靠 ZSet 本身持久化恢复
```

### 二、实测（MySQL 8.4.11 / Redis 7.4.11 / PHP 8.4.25）

脚本 `../bench/design/04-order-close.php`。为了能看清「重复关闭」，建了三张表：
`orders`（订单）、`close_attempt`（**不加任何唯一约束**，每一次关闭动作都记一条，用来数重复次数）、
`close_log`（`uk_order` 唯一约束，用来验证唯一键方案）。

#### A) 定时轮询扫表

| 轮询间隔 | 轮询次数 | 关闭订单 | 关闭延迟（平均/最小/最大 ms） | `Handler_read_next` 增量 |
| ---: | ---: | ---: | ---: | ---: |
| 1000 ms | 4 | 100 | **532.0 / 532.0 / 532.0** | 0 → **215** |
| 100 ms | 40 | 100 | **40.0 / 40.0 / 40.0** | 0 → **215** |

三个数字值得看：

- **平均延迟 ≈ 轮询间隔 / 2**：1000 ms 间隔 → 532 ms，100 ms 间隔 → 40 ms。到期时刻在间隔内近似均匀分布，取中点。
- **最小 = 最大**：因为 100 张订单是同一条 `INSERT` 按同一个 `NOW(3)` 创建的，`expire_at` 完全相同，
  又被同一次轮询、同一条 `UPDATE` 关掉，所以延迟一模一样。真实场景下单时刻分散，延迟会摊成一个区间。
- **`Handler_read_next` 增量两次都是 215**：间隔缩短到 1/10，轮询次数从 4 涨到 40，
  **索引总扫描量没变**。多出来的 36 次空轮询几乎不花钱 —— 因为空轮询走索引 seek，
  扫到 `expire_at > NOW()` 就停，一个数据行都不读。
  **「轮询间隔调小会把数据库打爆」这个担心，在走对索引的前提下是多余的。**

#### B) Redis 过期键 + keyspace notification

```
notify-keyspace-events: '' → 'Ex'（跑完已恢复为 ''）
写入 100 个 1000 ms 过期的 key，订阅 __keyevent@0__:expired
收到通知 100 / 100 个
通知延迟 ms：最小 4.9 / 中位 73.8 / 最大 132.8
```

- **最小 4.9 ms** 说明事件本身是快的；
- **中位 73.8 ms、最大 132.8 ms** 说明绝大多数 key **不是到点就发**的 ——
  这就是「惰性 + 定期采样」的直接体现。Redis 的定期删除每轮只采样一部分 key，
  没被采样到的 key 会一直等到有人访问或者下一轮采样，事件才发出来。
- **100/100 收到** 只代表这次运气好（100 个 key 在同一个采样周期内被扫到）。
  真正的问题是 pub/sub **不持久**：订阅者重启的那几秒，到期通知全丢，且没有任何补偿机制。
  **所以方案 B 必须配一个兜底对账**（比如每小时扫一次「已过期但状态还是待支付」的订单），
  否则单靠它一定会漏。

#### C) 延迟队列（ZSet）

先标定一次空轮询间隔（`ZRANGEBYSCORE + usleep(10ms)`），用来区分「机制精度」和「环境噪声」：

```
【标定】空轮询一轮实测 10.7 ms
```

| worker 数 | 关闭订单 | ZSet 剩余 | 关闭延迟 平均 / 最小 / 最大 (ms) | 压 ZSet 耗时 (ms) |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 100 | 0 | 329.7 / **6.0** / 665.0 | 52 |
| 4 | 100 | 0 | 196.0 / **23.0** / 345.0 | 51 |

**读法**：
- **最小延迟 6~23 ms 与标定的 10.7 ms 同量级** —— 这是机制本身的精度。
- **平均延迟远大于最小值**，因为 100 张订单**同时**到期，worker 只能一张一张关：
  第 100 张要等前面 99 张处理完。**平均延迟 ≈ (同时到期的订单数 / worker 数) × 单张处理耗时 / 2。**
- 这组数字**在机器空载时重跑过**。首轮实测时这台 Redis 被同一宿主上的其他任务以
  **23,244 ops/sec** 打着（slowlog 112 条），1 个 worker 那组平均延迟飙到 568.9 / 1319.6 ms、
  max 甚至 10757 ms，两轮之间毫无一致性；空载重跑后 1 worker 平均降到 329.7 ms。
  **判据始终是「最小延迟贴着标定值」** —— 最小值不受排队影响，平均值受。

> 测量方法上踩的坑值得记一笔：最初 score 用的是
> `UNIX_TIMESTAMP(expire_at)*1000 + MICROSECOND(expire_at)/1000`，测出来延迟稳定比轮询间隔大几百毫秒，
> 而且**每次跑的数都不一样**（884 / 550 / 1043 ms），极难怀疑到 SQL 表达式头上。
> 真因：`UNIX_TIMESTAMP()` 作用在 `DATETIME(3)` 上**已经带小数秒**（返回 `1789883542.878` 这种），
> 再加一遍 `MICROSECOND()/1000` 就把小数算了两次，score 比真实到期时刻最多晚 999 ms。
> 改成 `ROUND(UNIX_TIMESTAMP(expire_at) * 1000)` 后，最小延迟立刻从 884 ms 掉到 13 ms。

#### D) 不重复关闭：4 个 worker 同时处理 100 张已到期的订单

| 实现 | 生效关闭 | 被幂等拦下 | **实际关闭动作** | **重复关闭的订单** | 单张最多关几次 | 耗时(s) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| D1 无保护（`status` 不守卫） | **400** | 0 | **400** | **100 / 100** | **4** | 1.30 |
| D2 状态机 `WHERE id=? AND status=0` | 100 | **300** | **100** | **0** | 1 | 0.56 |
| D3 唯一约束 `close_log.uk_order` | 100 | **300** | **100** | **0** | 1 | 0.72 |

**D1 是这题的核心证据：100 张订单被关闭了 400 次，每一张都被重复关闭，最多的被关了 4 次**
（4 个 worker 抢同一批，每个都关了一遍）。落到业务上就是：**4 条退款记录、4 条库存回滚、4 条短信。**
而且 D1 的耗时反而更长（1.30 s vs 0.56 s）—— 多做的 300 次关闭动作全是白干的。

D2 和 D3 都能做到 0 重复，区别在**防护位置**：

```
D2 状态机：把「判断」和「修改」压成一条 SQL
   UPDATE orders SET status=2 WHERE id=1 AND status=0
   → 影响行数 = 1：我抢到了，继续做后续动作（退款、回滚库存）
   → 影响行数 = 0：别人已经关了，直接返回

D3 唯一约束：先干活，干完insert一条流水，靠唯一键挡住重复
   INSERT INTO close_log (order_id, ...) VALUES (1, ...)
   → 成功：我抢到了
   → 1062 Duplicate entry：别人已经关了，回滚本次动作
```

**两者都需要，不是二选一**：状态机管住「订单主表」的重复更新，唯一约束管住「副作用」的重复执行。
真实项目里副作用往往不止一个（退款、回滚库存、发通知），状态机只能保证主表被改一次，
**每个副作用都需要自己的幂等键** —— 这就是 D3 存在的理由。

### 三、四个反直觉的点

**1. 轮询间隔缩短 10 倍，数据库的索引扫描量没变。**
1000 ms → 100 ms，轮询次数 4 → 40，`Handler_read_next` 增量两次都是 **215**。
空轮询走索引 seek，扫到第一个不满足条件的行就停，一个数据行都不读。
**「轮询太密会打爆数据库」在走对索引时是个伪命题**，真正要担心的是「没走索引的全表扫描」——
那才是每轮扫 100 万行。

**2. Redis 的过期键通知不是「到点就发」。**
实测 100 个 1000 ms 过期的 key，通知延迟**最小 7.6 ms、中位 148 ms、最大 190 ms**。
Redis 的过期是「惰性删除 + 定期采样」：到点只是「可以被删了」，
真正删掉要看有没有人访问、或者定期任务有没有采样到。
依赖它做准时任务是**系统性偏差**，不是偶发抖动。更致命的是 pub/sub 不持久，掉线期间的到期事件永久丢失。

**3. ZSet 队列的最小延迟是毫秒级，平均延迟是「排队时间」。**
最小延迟 9~18 ms（贴着 10.5 ms 的轮询间隔），但 100 张订单同时到期时平均延迟 200~1300 ms。
**这两个数不矛盾**：前者是机制精度，后者是「100 张订单排队 + 共享 Redis 被邻居脚本打满」的排队时间。
所以 ZSet 队列的容量规划要看**峰值同时到期数**，不是看单条延迟。
高峰期要么加 worker，要么把到期时间打散（下单时给 `expire_at` 加几十毫秒随机抖动）。

**4. 不加防护时「重复关闭」的严重程度是 worker 数的倍数。**
4 个 worker → 400 次关闭动作、单张最多关 4 次。如果有 20 个 worker，就是 2000 次、单张最多 20 次。
**重复次数 = worker 数，不是「偶尔多一次」。** 而且加了守卫之后，被拦下的比例是 **300/400 = 75%** ——
也就是说，**四分之三的关闭动作本来就是重复的、白做的**。守卫不只是防事故，也在砍掉 75% 的无用功。

### 四、实战结论

| 场景 | 选择 | 实测依据 |
| --- | --- | --- |
| 订单量小、精度要求不高（分钟级） | 定时轮询扫表，间隔 60 s | 延迟 ≈ 间隔/2 = 30 s，`Handler_read_next` 增量恒定 |
| 订单量大、要求秒级 | 延迟队列（ZSet），多 worker | 最小延迟 9~18 ms，只捞到点的几个 |
| 已有 MQ | 延迟消息（RabbitMQ 死信队列 / RocketMQ 延迟消息） | 本机未实测，机制与 ZSet 同源 |
| 想「零轮询」 | Redis 过期键 + 监听，**但必须配对账兜底** | 中位延迟 148 ms，pub/sub 掉线丢事件 |
| 防止重复关闭 | 状态机 `WHERE status=0` + 副作用各自带唯一键 | 400 次动作 → 100 次，重复 0 |
| 多 worker 分片 | ZSet 天然支持：`ZREM` 返回值就是抢占结果 | 4 worker 抢 100 张，生效 100 / 被拦 300 |
| 峰值同时到期 | 加 worker，或给 `expire_at` 加随机抖动 | 平均延迟 ≈ (同时到期数/worker数) × 单张耗时 / 2 |
| 排查重复关闭 | 建一张 `close_attempt`（**不加唯一约束**） | 这是唯一能量出「重复了几次」的表 |

### 五、可能的追问

| 追问 | 要点 |
| --- | --- |
| 轮询扫表怎么避免扫全表？ | 必须走 `(status, expire_at)` 联合索引；实测空轮询几乎零成本 |
| 多个实例同时轮询会重复处理吗？ | 会。要么抢分布式锁（只有一个实例扫），要么靠状态机 + 唯一键兜住 |
| `LIMIT 500` 是为什么？ | 防止一次捞太多把内存打爆；剩下的下一轮继续，不会漏 |
| 订单非常多，一轮扫不完怎么办？ | 用 `id > 上次最大id` 翻页，或按 `expire_at` 分片给多个 worker |
| Redis 过期通知丢事件怎么发现？ | 配一个低频对账任务（每小时扫一次「已过期但状态还是待支付」）；有对账就不怕丢 |
| `notify-keyspace-events` 配什么？ | `Ex`（E = keyevent，x = 过期事件）；实测跑完要恢复原值，别改了不还原 |
| ZSet 队列重启后会丢吗？ | 不会，ZSet 本身持久化；但「已 ZREM 正在处理」的会丢，需要 processing 队列兜底 |
| `ZREM` 的返回值怎么用？ | `ZREM` 返回 1 表示抢到，返回 0 表示别人抢先了 —— 这是天然的分布式抢占原语 |
| 状态机和唯一约束选一个行不行？ | 不行。状态机管主表更新，每个副作用（退款/回滚库存/通知）要自己的幂等键 |
| 唯一约束冲突了要不要回滚事务？ | 要，但注意 1062 是「业务预期内」的异常，别让它把整个事务标记成失败 |
| 关闭延迟要求 1 秒内，怎么做到？ | 轮询 100 ms（实测延迟 30 ms）或 ZSet 队列（最小 9 ms），别用 Redis 通知（中位 148 ms） |
| 已支付的订单不能被超时关闭怎么办？ | 状态机守卫要写成 `WHERE status = 0`（待支付），支付回调改状态时用 `WHERE status = 0` 抢同一把锁 |

## Q48. 讲一个你最有挑战的项目：背景、你的角色、难点、结果。

> **本题未做实测，也不该实测。** 它问的是「你亲身做过什么」，任何数字都只能来自你自己的经历。
> 下面给的是答题框架、可套用的模板、以及反面示例。**模板里的数字是占位示例，必须换成你自己的。**

### 面试官在听什么

这题表面问项目，实际在验三件事，**没有一件是「你用过什么技术」**：

| 面试官真正在验的 | 从哪句话里听出来 | 答砸的信号 |
| --- | --- | --- |
| **你做的决策，还是你参与的决策** | 「我判断…因为…所以我选了…」 | 「我们团队用了…」「领导让我做…」 |
| **你遇到困难时的思考过程** | 「卡在…我怀疑…验证发现…」 | 「挺顺利的」「网上搜了一下就解决了」 |
| **你的技术判断力有没有边界** | 「这个方案的代价是…我当时没考虑到…」 | 「这个方案是最优的」「没有缺点」 |

**外加一条隐含项：这个人好不好合作。** 讲项目时把功劳全揽、把锅全甩的，技术再好也会被扣分。

### 回答框架（STAR，3~4 分钟）

时间分配是硬约束，**超 5 分钟面试官会开始走神**：

```
0:00 ─ 0:30   S/T 背景与目标   ← 30 秒讲完，只讲「为什么这件事难」
0:30 ─ 1:00   A 我的角色       ← 30 秒，必须说清「几个人、我负责哪块、我拍板了什么」
1:00 ─ 2:30   A 难点（核心）   ← 90 秒，2~3 个难点，每个都是「卡住 → 假设 → 验证 → 结论」
2:30 ─ 3:10   R 结果           ← 40 秒，数字 + 业务价值 + 代价
3:10 ─ 3:30   收尾             ← 30 秒，「如果重来我会怎么改」
```

**四段的写法要求，逐条对照：**

| 段 | 必须包含 | 必须不包含 |
| --- | --- | --- |
| 背景 | 业务规模（量级 + 峰值）、原来的痛点、目标数字 | 公司业务介绍、组织架构、产品功能 |
| 角色 | 团队人数、**我负责的具体模块**、我做的技术决策 | 「我们团队」「大家一起」（听不出你干了啥） |
| 难点 | **卡住的现场**、当时的假设、怎么验证的、最后怎么解决 | 「用了 Redis」「用了 MQ」（这是选型不是难点） |
| 结果 | 优化前后数字、业务收益、**付出的代价** | 「提升明显」「效果很好」这种没有数字的话 |

**难点的标准句式**（这是整段回答最值钱的部分，务必背熟）：

> 「最难的是 ____。现象是 ____，我一开始以为是 ____，验证之后发现其实是 ____。
> 试过 ____ 但不行，因为 ____。最后用 ____ 解决，代价是 ____。」

一句话里包含了**现象 → 假设 → 证伪 → 结论 → 权衡**，这就是面试官想听的思考过程。

| --- | --- | --- |
| 项目排期文档 / 周报 | 哪一周延期了、为什么延期 | 「卡在某个技术问题上两天」——这就是难点 |
| 上线记录 / 变更单 | 哪次上线回滚了 | 最真实的难点，且带具体后果 |
| 自己当时骂过的脏话 | 哪个 bug 查了一整天 | 最好的素材，因为你记得所有细节 |

**数字口径必须说清**，否则面试官一追问就露馅：

| 说「QPS 从 200 提到 2000」 | 必须补充 |
| --- | --- |
| 是峰值还是均值？ | 说「**峰值**从 200 提到 2000」 |
| 怎么测的？ | 「用 <压测工具> 在 <机器配置> 上压的」或「线上监控的 <指标>」 |
| 什么数据量下？ | 「<N> 万行数据、<M> 并发下」 |
| 哪个指标？ | 「**p99** 从 X ms 降到 Y ms」（p99 比均值有说服力得多） |

### 反面示例

| 面试官听到的回答 | 为什么扣分 | 改写成什么 |
| --- | --- | --- |
| 「我负责订单模块，用了 Redis 做缓存、RabbitMQ 做异步。」 | **选型不是难点**。任何人都能说这句话，听不出你的判断 | 「订单查询的 p99 卡在 800 ms，我压测发现是 <原因>，所以选了 <方案>，因为 <对比理由>」 |
| 「这个项目挺顺利的，没遇到什么坑。」 | **等于说这项目没价值**，或者你没深度参与 | 「最大的坑是 <X>，当时 <现象>，我们排查了 <多久> 才发现是 <原因>」 |
| 「架构是我设计的。」（工作 2 年） | 面试官不信，反而怀疑你在吹 | 「<某模块> 的 <某个具体决策> 是我做的，因为 <理由>」 |
| 「性能提升了 300%。」 | **没有口径的数字等于没数字** | 「订单列表接口 p99 从 1.2 s 降到 380 ms（线上监控，7 天均值），数据量 300 万行」 |
| 「都是产品天天改需求，不然早做完了。」 | **甩锅信号**，面试官会想「你进我团队也这样」 | 「需求变更时我们加了 <某机制>，后来变更的返工量降了 <数字>」 |
| 「这个方案是最优的，没有缺点。」 | **没有权衡意识**，资深岗最忌讳 | 「这个方案的代价是 <代价>，当时接受了，因为 <理由>」 |
| （讲了 8 分钟还没到结果） | **表达没有结构**，沟通能力扣分 | 严格按 30s / 30s / 90s / 40s / 30s 分配 |

**四个绝对不能说的话：**
1. **「我们」开头、全程没有「我」** —— 面试官无法判断你的贡献。
2. **「网上搜的」「照着教程做的」** —— 直接说明你没有独立解决问题的能力。
3. **「这不是我的锅」** —— 哪怕真的不是，也要说「当时的流程缺陷是…」，讲流程不讲人。
4. **「大概」「应该」「好像」** —— 数字记不清就说「具体数字我记不清了，量级是 <X>」，比含糊强。

### 可能的追问

| 追问 | 要点 |
| --- | --- |
| 这个方案有什么缺点？ | 必须能说出 1~2 个真实缺点。说「没有缺点」等于说「我没深入想过」 |
| 如果数据量再涨 10 倍，这套还撑得住吗？ | 说清瓶颈会先出现在哪一层，以及你会怎么改。答「撑不住，因为 <原因>」比硬撑好 |
| 为什么不用 <另一个方案>？ | 要能说出对比理由（成本 / 团队熟悉度 / 运维复杂度），不是「没想到」 |
| 你在其中具体写了多少代码？ | 老实说。资深岗不要求你写最多，但要求你知道每个细节 |
| 如果重来你会怎么做？ | **必须有答案**。答「不会改」显得自满；能说出改进项说明你会复盘 |
| 结果是怎么量出来的？ | 说清工具、时间窗口、数据量。这是验证你有没有真做过的问题 |
| 团队里有人反对你的方案吗？ | 好的回答：「有，他的理由是 <X>，我们用 <方式> 验证后选了 <Y>」——证明你会合作 |

## Q49. 讲一次线上故障：发现、止损、定位、恢复、复盘。

> **本题未做实测，也不该实测。** 下面给的是答题框架、时间线模板和反面示例。

### 面试官在听什么

故障题的**隐藏考点是「你的第一反应是什么」**。面试官在判断：

| 面试官真正在验的 | 答对的信号 | 答砸的信号 |
| --- | --- | --- |
| **你是不是先止血、再找根因** | 「我第一件事是 <回滚/降级/扩容>，先恢复服务」 | 「我先去翻日志找原因」——**这是最致命的错误** |
| **你的监控能力** | 「<监控指标> 在 <N> 分钟内触发告警」 | 「用户投诉了我们才知道」——要主动承认这是问题 |
| **你的定位方法论** | 「我按 <分层/二分/对比> 缩小范围，排除了 <X>」 | 「试了半天，最后发现是…」（听起来靠运气） |
| **复盘有没有闭环** | 「改进项 <X> 上线后，同类问题再没出现过」 | 「写了个复盘文档」（然后呢？） |
| **你的诚实度** | 主动说自己的失误，并说清流程缺陷 | 全程「不是我的问题」 |

> **止损优先于定位，这是故障处理的铁律，也是这题的第一考点。**
> 面试官最怕招进来一个「故障时非要先搞清楚为什么」的人。

### 回答框架（时间线叙事，4~5 分钟）

故障题**不要用 STAR，要用时间线**。按分钟讲，因为「多久恢复」本身就是关键指标。

```
0:00 ─ 0:20   一句话定性：「<时间>，<系统> 出现 <现象>，影响 <范围>，<N> 分钟恢复」
0:20 ─ 1:00   发现：谁发现的、怎么发现的、告警延迟多久
1:00 ─ 1:40   止损：**做了什么让服务先恢复**、多久恢复的
1:40 ─ 3:00   定位：怎么一步步缩小范围到根因（**这段是技术深度所在**）
3:00 ─ 3:40   恢复与验证：怎么确认真的好了、有没有二次故障
3:40 ─ 4:30   复盘：根因 + 流程缺陷 + 改进项 + 改进后的效果
```

**每一段的写法要求：**

| 段 | 必须包含 | 常见错误 |
| --- | --- | --- |
| 定性 | 时间、影响面（多少用户 / 多少订单）、恢复时长 | 铺垫太久，面试官听了 2 分钟还不知道出了什么事 |
| 发现 | **告警还是投诉**、告警延迟、第一个指标异常是什么 | 回避「是用户投诉发现的」 |
| 止损 | **具体动作**（回滚 / 降级 / 限流 / 切流）+ 耗时 | 跳过止损直接讲定位 |
| 定位 | 每一步排除掉什么、用了什么工具、**当时的假设与验证** | 「最后发现是…」（中间过程全无） |
| 恢复 | 怎么验证的、观察了多久才敢说恢复 | 只说「恢复了」，不讲验证 |
| 复盘 | 根因（技术）+ 缺陷（流程）+ 改进项 + **改进后的效果** | 只讲技术根因，不讲流程缺陷 |

**定位过程的标准句式**（技术深度的体现）：

> 「现象是 <A>，我先看了 <指标 1>，正常，所以排除了 <层 1>。
> 再看 <指标 2>，发现 <异常>，怀疑是 <假设>。
> 用 <工具/方法> 验证，确认/推翻了假设，最后定位到 <根因>。」

### 可套用的模板

```
【定性】<日期> <时间>，<系统> 出现 <现象>，影响 <N> 个用户 / <M> 笔订单，
       持续 <T> 分钟。
【发现】<时间> <监控系统> 触发 <指标> 告警。[如果是对账/客服发现的，**主动说**：
       「这次是客服反馈才发现，说明我们的监控缺 <某指标>，这是复盘的第一条改进项」]
【止损】我第一件事是 <回滚版本 / 摘掉节点 / 降级某功能 / 限流>，
       在 <T1> 分钟内让服务恢复。[**止损一定要在定位之前讲**]
【定位】恢复后开始定位。现象是 <A>，先看 <指标 1> 正常 → 排除 <层 1>；
       再看 <指标 2>，发现 <异常> → 怀疑 <假设>；
       用 <工具> 验证 → 确认根因是 <根因>。
       [如果有误判，也要讲：「中途我一度以为是 <错误方向>，后来用 <证据> 排除了」]
【恢复】修复后 <灰度 / 观察 N 分钟>，<指标> 回到正常水位，没有再复发。
【复盘】技术根因是 <根因>；但**流程缺陷是 <为什么没在测试环境发现 / 为什么没有熔断>**。
       改进项：① <监控项> ② <流程> ③ <代码>。
       **<改进项> 上线后，同类问题再没出现过 / 下一次 <类似场景> 时被 <改进项> 提前拦住了。**
```

**故障素材清单**（面试前把这些数字查出来，写在一张纸上）：

| 要查的数 | 为什么重要 |
| --- | --- |
| 故障起止时间、持续多久 | 恢复时长是故障题的核心指标 |
| 影响多少用户 / 订单 / 金额 | 量化影响面，证明你知道业务严重性 |
| 告警延迟（几分钟发现的） | 反映监控能力，也是复盘改进项 |
| 止损动作和耗时 | **第一考点**，必须有具体动作和分钟数 |
| 根因的一句话描述 | 要能用一句话说清，不能绕 |
| 改进项 1~3 条 + 落地情况 | 证明复盘闭环，不是写文档了事 |

**改进项要分层写，不要只写技术：**

```
技术层：加索引 / 改配置 / 修代码 / 加缓存
监控层：加告警指标 / 缩短告警延迟 / 加对账任务
流程层：变更前必须灰度 / 高危操作双人复核 / 压测通过才能上线
```

**三层都有，才说明你理解「故障是流程问题，不只是代码问题」。** 只讲技术层的复盘，面试官会认为你下次还会再犯。

### 反面示例

| 面试官听到的回答 | 为什么扣分 | 改写成什么 |
| --- | --- | --- |
| 「我先去查日志找原因。」 | **最致命**：服务还在挂，你先去研究了 | 「我先回滚了版本，服务 3 分钟恢复，然后才开始查日志」 |
| 「是用户投诉了我们才知道。」 | 诚实是好的，但**不能就这么结束** | 「客服反馈才发现，说明监控缺 <指标>，这成了复盘的第一条改进项，现在 <指标> 已加告警」 |
| 「重启就好了。」 | 面试官会问「然后呢」，而且听起来你不关心根因 | 「重启是止血，但我知道这不是根因，所以继续查到 <根因>」 |
| 「这不是我写的代码 / 不是我的锅。」 | **甩锅信号**，一票否决 | 「这段代码的历史原因我了解过了，当时的流程缺陷是 <X>」 |
| 「加了个索引就好了。」 | 没有讲定位过程，听不出能力 | 「我用 <工具> 看到 <现象>，怀疑是慢查询，用 <方式> 验证后加了索引」 |
| 「复盘文档写得很详细。」 | 文档不是结果，**闭环才是** | 「改进项 <X> 上线后，同类问题再没出现过」 |
| 「影响不大，就几个人受影响。」 | 显得你不重视 | 「影响 <N> 个用户，我们按 <口径> 统计的，这是我们的责任」 |
| （全程没有人名、没有时间点） | **听起来像编的** | 「14:05 告警，14:08 回滚完成，14:35 定位到根因」——时间点让叙述可信 |

**四个绝对不能说的话：**
1. **「跟我没关系」** —— 面试官会想「出事了你会不会也这么说」。
2. **「重启就好了，我也不知道为什么」** —— 说明你没有好奇心，这是技术岗的硬伤。
3. **「我们没写复盘」** —— 说明团队没有工程文化，你自己也没推动。
4. **「影响不大」** —— 轻视故障的人，下一个故障会更大。

### 可能的追问

| 追问 | 要点 |
| --- | --- |
| 如果是你写的代码导致的，你会怎么讲？ | 老实讲，重点放在「我怎么发现的 / 改进了什么」，不放在「谁写的」 |
| 为什么测试环境没发现？ | 说清测试环境和线上的差异（数据量 / 并发 / 配置），以及你怎么改进这个差异 |
| 止损和定位哪个优先？ | **止损优先**。除非定位只需要 1 分钟，否则先恢复服务 |
| 怎么确认真的恢复了？ | 说清验证指标和观察时长，不能只说「看起来好了」 |
| 复盘会怎么开？ | 对事不对人；根因要挖到流程层；改进项要有 owner 和 deadline |
| 改进项真的落地了吗？ | 说清落地情况和效果。**没落地就老实说没落地**，别编 |
| 如果同类故障再来一次，多久能恢复？ | 用改进后的数据回答（更快）或诚实说「还是会慢，因为 <原因>」 |

## Q50. 讲一次性能优化，给出优化前后的量化指标和验证方法。

> **本题未做实测，也不该实测。** 下面给的是答题框架、指标模板和反面示例。

### 面试官在听什么

这题是**最容易答得空泛**的一题。面试官全程只做一件事：**追问你的数字是怎么来的。**

| 面试官真正在验的 | 答对的信号 | 答砸的信号 |
| --- | --- | --- |
| **你有没有先定位瓶颈、再动手** | 「我先用 <工具> 看到了 <证据>，才发现瓶颈在 <层>」 | 「我加了 Redis 缓存」（拍脑袋优化） |
| **你懂不懂指标口径** | 「p99 从 1.2 s 降到 380 ms」 | 「响应快了很多」（等于没说） |
| **你的验证方法可信吗** | 「压测前先 <预热>，跑 3 轮取中位数，数据量 <N> 万行」 | 「优化完感觉快了」 |
| **你能不能证明是这次改动带来的** | 「灰度 1 台观察，回滚后数字回到原值」 | 「那段时间正好 <别的原因>」 |
| **你有没有识别出上限和代价** | 「再往下优化要改协议，收益不划算，所以停在这」 | 「还能再快，只是没时间」 |

> **这题的核心不是「你优化了多少」，而是「你怎么知道是你优化的」。**
> 没有对照、没有回滚验证的数字，面试官会直接归零。

### 回答框架（5 分钟）

```
0:00 ─ 0:30   问题与影响：什么场景慢、慢到什么程度、影响了谁
0:30 ─ 1:00   定位：用什么工具、看到什么证据、排除掉什么
1:00 ─ 2:00   假设与验证：怀疑什么、怎么证实的
2:00 ─ 3:30   优化：改了什么（**按收益排序，先讲收益最大的那条**）
3:30 ─ 4:30   量化：优化前后对比表 + **验证方法** + 代价
4:30 ─ 5:00   边界：还能怎么优化、为什么停在这
```

**每一步的要求：**

| 段 | 必须包含 | 常见错误 |
| --- | --- | --- |
| 问题 | 场景（哪个接口 / 哪条链路）+ 指标 + 影响面 | 「系统很慢」（哪个系统？多慢？） |
| 定位 | **工具名 + 看到的证据** | 跳过定位，直接讲优化手段 |
| 验证 | 假设 → 怎么证实 → 结论 | 没有假设，直接改 |
| 优化 | 改动列表，**按收益降序** | 讲得平均用力，听不出哪条最值钱 |
| 量化 | **优化前后对比表**（见下）+ 验证方法 | 只有一个「提升 X 倍」 |
| 边界 | 剩余瓶颈 + 停手理由 | 「没有瓶颈了」 |

### 可套用的模板

**优化前后的对比表**（这张表就是这题的答案主体，务必手写出来背熟）：

| 指标 | 优化前 | 优化后 | 变化 | 口径 |
| --- | ---: | ---: | ---: | --- |
| p50 | <A> | <B> | <-X%> | 线上监控，7 天均值 |
| **p99** | <A> | <B> | <-X%> | 线上监控，7 天均值 |
| 峰值 QPS | <A> | <B> | <+X%> | 压测，<机器配置> |
| CPU 使用率 | <A>% | <B>% | <-X%> | 同负载下 |
| 慢查询数 / 分钟 | <A> | <B> | <-X%> | MySQL slow log |
| 机器数 | <A> 台 | <B> 台 | <-X%> | 直接成本 |

**六条铁律，逐条对照自己的稿子：**

1. **p99 比均值重要。** 说「平均响应从 200 ms 降到 100 ms」的说服力，远不如「**p99 从 1.2 s 降到 380 ms**」——
   平均值会被大量快请求拉低，用户投诉的永远是 p99。
2. **必须说明是压测还是线上。** 压测要给出并发数、数据量、机器配置；线上要给出时间窗口。
3. **必须给出对照。** 前后是同一套压测条件吗？同数据量吗？同机器吗？没控制变量的数字会被直接追问。
4. **必须能证明因果。** 最强的是**回滚验证**：「灰度 1 台机器跑优化后的版本，p99 是 380 ms；
   另外 7 台没改的仍是 1.2 s」——同一时刻的对照，排除了所有环境变量。
5. **必须讲代价。** 加了缓存的代价是一致性延迟；加了索引的代价是写入变慢、磁盘变大。
   **讲不出代价的优化，面试官会认为你没在生产环境待过。**
6. **必须讲停手理由。** 「再优化要改成 <成本更高的事>，收益只有 <X>，不划算」——
   这说明你会算投入产出比，比「我还能优化」高一个层次。

**验证方法的四个层次，从弱到强：**

```
第 1 层（最弱）：优化完，自己点了下页面，感觉快了            ← 面试官会直接跳过
第 2 层：压测工具跑一遍，看指标                              ← 及格
第 3 层：压测前预热、跑 3 轮取中位数、控制数据量和机器一致     ← 良好
第 4 层（最强）：灰度发布，新旧版本同时在线对比；或回滚验证    ← 优秀，直接讲这个
```

**性能优化的标准句式**：

> 「我先用 <工具> 定位，看到 <证据>，排除了 <层>，确定瓶颈在 <层>。
> 猜测是 <假设>，用 <方法> 验证确认。
> 做了 <N> 项优化，收益最大的是 <第 1 项>，占了总收益的 <X>%。
> 优化后 **p99 从 <A> 降到 <B>**（线上监控，灰度对比）。
> 代价是 <代价>。再往下要 <更高成本的手段>，收益不划算，所以停在这。」

### 反面示例

| 面试官听到的回答 | 为什么扣分 | 改写成什么 |
| --- | --- | --- |
| 「我加了 Redis 缓存，性能提升很大。」 | **没定位 + 没数字**，双重扣分 | 「我用 Xdebug / 慢日志定位到 80% 时间在 <某查询>，加缓存后 p99 从 A 降到 B」 |
| 「响应时间从 200 ms 降到 100 ms。」 | 均值指标，且无口径 | 「**p99** 从 1.2 s 降到 380 ms（线上监控 7 天均值，灰度对比）」 |
| 「优化了 3 倍。」 | 哪个指标？怎么测的？ | 「压测吞吐从 800 QPS 提到 2400 QPS（8 核 / 10 万行数据）」 |
| 「我感觉快了不少。」 | 等于没做验证 | 「压测跑 3 轮取中位数，前后同机器同数据量」 |
| 「那段时间系统整体都在变快。」 | **自己否掉了因果关系** | 「灰度 1 台对比，未灰度的机器指标没变」 |
| 「没有代价，纯提升。」 | **不真实**，面试官不信 | 「代价是缓存和 DB 有最多 500 ms 的不一致，业务上可接受」 |
| 「还能更快，只是没时间做。」 | 显得没有成本意识 | 「再优化要换协议，收益只有 5%，投入 2 周，不划算」 |
| 「我优化了 SQL、加了缓存、调了参数、换了框架…」 | **平均用力**，听不出哪条最值钱 | 「三项优化，收益最大的是索引，占 70%；缓存占 25%；参数只占 5%」 |

**四个绝对不能说的话：**
1. **「提升很大 / 明显变快」** —— 没有数字的优化等于没做。
2. **「我加了很多优化」** —— 面试官只关心收益最大的那一项，列清单是虚的。
3. **「没有代价」** —— 生产环境的优化一定有取舍。
4. **「用压测工具随便跑了一下」** —— 「随便」两个字直接废掉你的数字。

### 可能的追问

| 追问 | 要点 |
| --- | --- |
| 这个数字怎么测的？ | 工具、并发数、数据量、机器配置、跑几轮、取什么统计量。**这是必问题，务必背熟** |
| 怎么证明是你的改动带来的？ | 灰度对比 / 回滚验证。这是最强证据，答不出会被判定为「蹭功劳」 |
| p99 为什么比 p50 重要？ | 平均值被大量快请求稀释；用户投诉和线上事故几乎都来自长尾 |
| 为什么只优化到这一步？ | 讲投入产出比：下一步的成本 vs 收益 |
| 这个优化有什么副作用？ | 缓存一致性 / 写入变慢 / 内存占用 / 复杂度上升。**必须能说出至少一个** |
| 如果流量再涨 10 倍，瓶颈会在哪？ | 说清下一个瓶颈的位置和你的预案 |
| 优化前你知道瓶颈在哪吗？还是试出来的？ | 老实说。试错了也要讲「我先怀疑 X，验证后排除了」——过程本身就加分 |
| 你是怎么发现这个问题的？ | 监控告警 / 用户反馈 / 日常巡检。说清发现渠道，体现你的监控意识 |
| 有没有做过失败的优化？ | **最加分的问题**。讲一个「改了反而变慢，回滚了」的例子，说明你会验证、会止损 |
| 这次优化沉淀成什么了？ | 文档 / 脚手架 / 监控指标 / 团队规范。体现你把个人经验变成了团队能力 |
